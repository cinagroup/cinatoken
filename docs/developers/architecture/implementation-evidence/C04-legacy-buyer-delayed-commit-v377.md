# C04 v377 delayed buyer COMMIT: provisional `unconfirmed`

2026-09-25. **Review only; default off.** This successor tests a visibility race left open by the [v376 COMMIT response loss evidence](./C04-legacy-buyer-commit-ack-v376.md). A buyer write may have sent `COMMIT` and lost its connection before PostgreSQL commits. The immediate [v375 read](../../../../packages/core/src/db/postgres/legacy-buyer-terminal-reader-v375.ts) can therefore return `unconfirmed` for a transaction that later becomes committed. `unconfirmed` means “not confirmed by this read”; it is never proof that another debit is safe.

## Proposed persistent recheck contract

This contract is **not installed or called by production code**. Before the financial writer starts, an independent durable journal must retain an immutable request intent ID, canonical complete request digest, user/API key/Workspace, attempt and quote identities, expected terminal financial facts, and a deadline. The journal must survive a process failure between sending `COMMIT` and observing its response. A stale `prepared` journal entry must be swept as potentially uncertain; setting `uncertain` only in the writer's exception handler is insufficient because that handler may never run.

An owned worker may take a lease on one journal entry and perform at most seven fresh, dedicated terminal-reader LOGIN probes at offsets **0, 1, 5, 20, 60, 180, and 600 seconds** from the first uncertain observation. Each probe closes its reader connection, records the observation and next due time durably, and performs no financial write. `unconfirmed` and reader errors remain pending through the schedule. After the last probe, the entry becomes a durable operator quarantine, not an authorization to retry the charge. `conflict` quarantines immediately. A v375 `confirmed` result records only **financial facts confirmed**: user success still requires the complete intent/result digest and request-scoped same-transaction proof for Guardrail rows, unreserved windows, audit, and daily statistics. Receipt retention must exceed the entire automated and operator review window; a pruned receipt is unresolved.

The production journal schema, immutable expectation receipt, worker lease, authenticated Provider result/bill binding, role grants, and read-path wiring remain to be designed and tested. The v376 wrapper is a single immediate observation with no replay branch; it is not this persistent scheduler.

## Native evidence

The [v377 native fixture](../../../../scripts/db/cutover/postgres-legacy-buyer-delayed-commit-v377.native.test.mjs) uses an owned local PostgreSQL 18.6 cluster and a [transparent delayed-COMMIT proxy](../../../../packages/core/src/test-support/postgres-delayed-commit-proxy-v377.mjs). It follows the real writer's extended `Parse`/`Bind`/`Execute` command chain, holds the original `Execute` and following `Flush`/`Sync` frame, disconnects the client while keeping the real PostgreSQL backend transaction open, and releases those exact bytes only after the independent reader returns `unconfirmed`. PostgreSQL documents that `Execute` runs a bound portal and `CommandComplete` follows portal execution; `pg_stat_activity.xact_start` being non-null means the writer transaction remains active. [PostgreSQL protocol](https://www.postgresql.org/docs/18/protocol-flow.html), [activity statistics](https://www.postgresql.org/docs/18/monitoring-stats.html).

A second new reader then observes `confirmed` and the same xid8 budget receipt after the database commits. This models intermediary delay after the client sent the command; it does not prove an already delivered COMMIT can remain pending inside PostgreSQL or alter TCP ACK packets. The fixture does not attempt a second financial write while the first transaction is still pending. Its no-replay evidence at that point is the v376 wrapper's single writer invocation and absence of a retry branch. A deliberate direct replay is tested only after the original COMMIT has completed, where v372 rejects it.

The fixture passed **11/11 stages, cleanup PASS** in the [machine report](./C04-legacy-buyer-delayed-commit-v377-report.json). The proxy observed one COMMIT Execute, one held and released frame group, and one real `CommandComplete(COMMIT)`. Before release, the new reader returned `unconfirmed`, the writer transaction remained open, the request log and economic event were invisible, and the buyer budget receipt count had not increased from the admission baseline. After release, another new reader returned `confirmed`; the log, event, audit, holds, one new budget receipt and one debit were visible, with the event and new receipt sharing xid8. No formal migration, remote SQL, production credential, Worker or Provider is changed.
