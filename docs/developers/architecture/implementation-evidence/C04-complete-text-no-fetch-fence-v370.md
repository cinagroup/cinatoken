# C04 v370: durable no-fetch send fence

2026-09-25. **Review only; non-activatable.** The [SQL proposal](../../../../packages/core/migrations-proposals/postgres/complete-text-no-fetch-fence-v370.sql) and [native fixture](../../../../scripts/db/cutover/postgres-complete-text-no-fetch-fence-v370.native.test.mjs) add one narrow proof for a v362 grant whose v365 send deadline has passed. They do not close the buyer transaction, release a hold, authorize an attempt 2, or prove a zero supplier charge.

## Decision and authority

The dedicated direct `NOINHERIT LOGIN` `cinatoken_gateway_complete_text_no_fetch_resolver` can call only `resolve_complete_text_no_fetch_v370(grant_id,resolution_nonce)`. The wrapper requires `READ COMMITTED`, reads the v362 request ID without a row lock, takes the same `(348,hashtext(request_id))` transaction advisory lock used by v365 custody and send-start, then re-reads the grant `FOR SHARE` and rejects identity drift. The insert triggers use that request-first order too. Only after the stored send deadline has passed does the resolver check for a committed v365 marker. An existing marker returns `possible_send_unknown`, including a marker with no `fetch_invoked` fact. The wrapper also refuses a contradictory non-attestation v366 fact. A holder `no_fetch_attestation` supplies no proof by itself.

With no marker, the transaction inserts one immutable `complete_text_no_fetch_resolutions_v370` row containing the stored grant, request, quote, attempt nonce, grant/upload hashes, optional custody holder run, send deadline, server fence time and `result='verified_no_fetch'`. The row is append-only, including a TRUNCATE guard. The same installation transaction adds `BEFORE INSERT` triggers to **both** v365 custody and send-start. Each trigger derives the request from the stored grant, takes the request lock and rejects insertion after the fence commits. The trigger also catches a privileged direct insert that bypasses a v365 wrapper. Existing v365 functions, v362 `obligation_state='unknown'`, ordinary/Guardrail holds and account/window counters are not changed.

This proof relies on the private holder rule that physical fetch requires a fresh v365 start whose PostgreSQL COMMIT and connection close were acknowledged. It proves absence of a *committed start* under that rule. It does not infer zero charge from an absent holder observation, a timeout or an ACK loss. A provider bill without a marker, a holder bypass or later contradictory evidence is an incident for separately authenticated intake and reconciliation. A replay with the same nonce returns `already_verified_no_fetch`; a different nonce returns `resolution_conflict`, with no new authority.

## Local proof

The [report](./C04-complete-text-no-fetch-fence-v370-report.json) records PostgreSQL 18.6, **1/1 native test and 19/19 stages**, with cluster cleanup confirmed. The fixture runs the formal 73 PostgreSQL migrations and relevant review-only v361/v362/v365/v366/v367 proposals against an owned loopback cluster. It then installs the separate [v370 renewed-holder-facts successor](../../../../packages/core/migrations-proposals/postgres/complete-text-renewed-holder-facts-v370.sql) before this no-fetch fence in the **same cluster**, confirming that both v370 successors can coexist with their installer checks and ACLs. This fixture exercises the no-fetch races; the [renewed-facts evidence](./C04-complete-text-renewed-holder-facts-v370.md) covers that writer's epoch behavior. It verifies:

| Case | Native observation |
| --- | --- |
| Default-off install, role drift, deliberate rollback | No partial table or trigger remains; one reviewed transaction installs both insert fences. |
| Direct LOGIN ACL | Resolver can call only its wrapper; holder, public runtime and provider-bill roles cannot resolve; resolver cannot read private tables, call send-start/renewal or `SET ROLE`. |
| Live deadline and committed start | Live deadline refuses resolution. A committed start remains `possible_send_unknown` after expiry; v362 remains unknown. |
| Expired grant without start | One `verified_no_fetch` row copies the stored identity after the server deadline; v365 custody and send-start direct inserts are rejected. Exact finite ordinary and Guardrail holds and counters do not change. |
| Direct resolver client | The [v372 client](../../../../packages/proxy/src/services/postgres-complete-text-no-fetch-v372.ts) uses the dedicated LOGIN and returns evidence only after its `READ COMMITTED` transaction commits and its connection close acknowledges. Same-nonce replay after an uncertain ACK returns the original immutable row. Its [synthetic tests](../../../../packages/proxy/src/services/postgres-complete-text-no-fetch-v372.test.ts) pass 8/8. |
| Holder `no_fetch_attestation` | The attestation before deadline grants no decision; after deadline, the database lock and absent marker supply the proof. |
| Rollback and lost ACK | A rolled-back resolution leaves no row. Replay after a committed result and closed connection returns the one row, while a conflicting nonce is refused. |
| Both commit orders | A start transaction holds the request lock across the deadline, so the resolver waits and returns possible-send unknown. A committed fence holds the lock while a holder start waits, then the holder receives no send authority. |

For speed, the fixture uses cluster-superuser fault injection to shorten a v362 send deadline *before* starting each race. Neither that update nor direct insertion is available to runtime roles. Same-cluster installation does not prove a concurrent renewed-fact versus fence race. This local SQL proof does not establish provider-source authentication, actual provider bytes, remote COMMIT/close ACK delivery, fleet drain, D1/MySQL parity, or Linux CI. The buyer request terminal, all-hold financial closer, late-bill adjustments and complete buyer writer cutover remain required by the [v368 closure contract](./C04-complete-text-result-resolution-financial-closure-contract-v368.md). **C04.1–8 and C04.G remain unchecked.**
