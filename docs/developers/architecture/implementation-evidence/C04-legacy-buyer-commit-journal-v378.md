# C04 v378 durable buyer COMMIT uncertainty journal

2026-09-25. **Review only; default off.** The [v378 SQL proposal](../../../../packages/core/migrations-proposals/postgres/legacy-buyer-commit-journal-v378.sql) and [TypeScript caller/worker](../../../../packages/core/src/db/postgres/legacy-buyer-commit-journal-v378.ts) implement a persistent uncertainty protocol for the narrow v372 legacy buyer write. They are not installed or called by production code. There is no financial writer invocation in the recheck worker and no retry branch in the journaled write caller.

## Boundary and state transitions

Before invoking `writeOnce`, the caller pins the v375 financial expectation and caller-supplied SHA-256 of the canonical complete request in a journal row. It awaits the prepare statement, closes that journal session, and requires a **different PostgreSQL backend** to see the committed row with the same digest. If either step fails, it never invokes the writer. A duplicate request ID cannot prepare a second row. The database blocks ordinary updates to the pinned expectation, request ID, digest, preparation timestamp, backend PID, and deadline. The writer callback is invoked at most once, including when it rejects with `undefined`.

The journal's `write_ack_at` is a **caller-reported observation**. Even an `acknowledged` report leaves the row `pending` and due for a terminal read. A lost status-update response leaves the committed `prepared` row available for recovery. A worker sweeps `prepared` rows older than 30 seconds as uncertain, covering a process exit before the writer or after a writer COMMIT without a status update. A stale row cannot authorize a new debit.

The worker atomically leases one due row with `FOR UPDATE SKIP LOCKED`, opens and closes a dedicated v375 terminal-reader LOGIN, and completes the lease through `complete_from_reader_v378`. That database function locks the journal row, reads the pinned expectation, calls the actual v375 financial reader under the terminal reader's `SESSION_USER`, and records the result in the same database call. The lock prevents two concurrent reader calls with one token. The journal LOGIN has no way to submit `confirmed`, `unconfirmed`, or `conflict`; it can record only `reader_error` after opening or reading fails. Direct table access and cross-role function calls are denied. A stale lease token or completion after lease expiry has no effect. The lease expiration check uses a fresh database clock value **after** acquiring the row lock. A faulty journal worker can consume claims by reporting reader errors, leading to quarantine; it cannot assert confirmed financial facts.

There are at most seven lease claims, including claims abandoned by a crashed worker. Timely completed probes target offsets 0, 1, 5, 20, 60, 180, and 600 seconds from the first uncertain observation. After worker downtime, each catch-up probe is spaced by at least 1, 4, 15, 40, 120, or 420 seconds following the previous result. `unconfirmed` and `reader_error` remain pending while claims and deadline remain; `conflict` quarantines immediately. A seventh inconclusive result or an expired seventh lease quarantines. The deadline also quarantines unattended entries. Quarantine is an operator-review state and never a retry permission.

`recheckLegacyBuyerJournalOnceV378` performs one worker step; `runLegacyBuyerRecheckBatchV378` stops at the first empty due queue and caps a pass at 32 rows. An external scheduler is still needed to wake for later due times.

`financial_facts_confirmed` means only that the **v375 checked financial subset** was read back: the buyer log, v2 economic event and attempts, producer transaction marker, budget receipt, ordinary hold, and narrow Guardrail terminal rows match the stored expectation. It is not a request-level success result. The journal stores a complete-request digest but **does not compare it to a writer-side, same-transaction receipt**. Model, route, protocol, Provider request/response bytes, independently authenticated Provider billing, Guardrail transaction identity, unreserved window changes, audit, and daily statistics remain outside this proof. The v375 budget receipt must remain retained throughout automated and operator review; that retention contract is not installed here. A pruned receipt remains `unconfirmed`.

## Native evidence and limits

The [owned PG18.6 fixture](../../../../scripts/db/cutover/postgres-legacy-buyer-commit-journal-v378.native.test.mjs) passed **18/18 stages with cleanup PASS** in the [machine report](./C04-legacy-buyer-commit-journal-v378-report.json). It verifies installation requires explicit activation, role separation, malformed and fractional intent rejection before a writer, second-backend visibility, immutability, advisory ACK, `Promise.reject(undefined)`, stale prepared recovery, synthetic loss of a committed prepare response, concurrent claims, lease reclamation, stale token rejection, discarded terminal completion response, pending reader errors, seven inconclusive observations, seven abandoned claims, immediate conflict quarantine, deadline quarantine, completion blocked across lease expiry, and the bounded batch runner. The report includes the seven durable probe rows and fresh reader backend PIDs. Privileged fixture time changes make the 600-second schedule testable without waiting ten minutes.

This fixture uses a controlled function with the v375 signature to vary financial statuses. Its writer callback only counts invocations. The [v375](./C04-legacy-buyer-terminal-reader-v375.md), [v376](./C04-legacy-buyer-commit-ack-v376.md), and [v377](./C04-legacy-buyer-delayed-commit-v377.md) fixtures separately exercise the real terminal reader and real buyer write, including delayed COMMIT visibility. **v378 does not yet prove the new journal against a real v372 write plus the real v375 reader in the same run.** It also does not physically cut a prepare COMMIT response or kill a process between prepare, writer COMMIT, and status update. Its synthetic response-loss case commits prepare, discards the caller-visible result, and proves the wrapper skips the writer while a second backend sees and later sweeps the row. The stale-prepared case simulates elapsed time; it is not a process-crash injection.

Before any activation, the separate journal LOGIN must be provisioned, the proposal reviewed as a migration, the journal session factory and worker scheduled, a real writer/reader combined crash and delayed-COMMIT fixture added, and complete request intent, Provider result/bill, side-effect transaction markers, and receipt retention gaps closed. Core `tsc --noEmit` remains red on unrelated existing test typings and missing `vitest`; it reports no diagnostic in the v378 TypeScript file. No formal migration, remote database, production credential, Worker, or Provider was changed.
