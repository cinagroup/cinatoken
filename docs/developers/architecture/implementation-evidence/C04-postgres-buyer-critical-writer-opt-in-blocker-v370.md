# C04 v370 buyer critical writer opt-in counterexample

2026-09-25. **Review only; no application writer switch.** The existing [PostgreSQL critical writer](../../../../packages/core/src/db/postgres/critical-writes.impl.ts) cannot yet call the [v369 transaction seam](../../../../packages/core/src/db/postgres/legacy-buyer-held-transaction-v369.ts) as a sound opt-in for a held `actual`/`actual` request. The [owned local PostgreSQL counterexample](../../../../scripts/db/cutover/postgres-buyer-held-opt-in-gap-v370.native.test.mjs) passed **1/1** on PostgreSQL 18.6 and cleaned up its cluster. It reproduces the privilege and read-committed window race below using only local fixture roles and the relevant table columns. It does not install v368 or run the whole critical writer.

## Where the direct integration breaks

The v369 helper can run on the existing Drizzle `tx`, so the log, audit and v2 economic event could share the settlement transaction. To match v368's lock order, the critical writer would have to take the request advisory lock before its current API-key `FOR UPDATE`, then call the v369 helper before log insertion. The current writer instead locks the ordinary reservation before the account and directly updates the account, ordinary reservation, Guardrail reservations and windows. Calling the helper after those writes would double count and invert the v368 account-before-reservation order.

Even if those direct held writes are replaced, the critical writer's final `UPDATE guardrail_budget_windows` accounts positive charges in any applicable user or API-key window that has **no matching request reservation** (`critical-writes.impl.ts:939–960`). The [v368 counter policy](../../../../packages/core/migrations-proposals/postgres/buyer-split-counter-grant-policy-v368.sql) revokes the buyer's direct `UPDATE` privilege on this table. PostgreSQL rejects that final UPDATE with `42501` even when the predicate would update zero rows. The same policy makes `SELECT … FOR UPDATE` on the table fail with `42501` for the buyer. Merely skipping the final statement leaves an accounting hole.

The native counterexample starts with a held user window, then checks for unreserved windows under the read-committed isolation required by v368. A second connection creates an applicable API-key window with no reservation before the first transaction commits. A subsequent read in the first transaction sees the new window; an opt-in that skipped the final UPDATE would leave its `unreserved_micros` at **0**. Running the current writer's predicate under a privileged fixture role increases it to **1**. A preflight read therefore cannot establish that there will be no unreserved scope at commit, and buyer lacks the table privileges to lock such rows directly. Any replacement needs a reviewed database-side authority and a serialization rule covering window creation, so the check and accounting transition cannot diverge.

The v368 SQL also accepts caller-provided ordinary and Guardrail micros anywhere from zero to each reserved ceiling. The v369 helper checks role, isolation and returned values, but neither layer authenticates an immutable buyer result or Provider bill. The critical writer checks `chargedCost` against the request log input and writes a v2 `actual` event in the same transaction; those are still caller-supplied facts. That is insufficient for the C04 financial closure gate.

## Required cutover work

1. Extend one request-scoped database operation, under the same buyer transaction, to cover the held and applicable unreserved windows with an explicit lock and scope-creation protocol. Preserve request → API key → account → reservation tables/rows → windows order and reject unsupported states before any financial write.
2. Bind the ordinary and Guardrail amounts to a reviewed immutable final buyer fact and trusted Provider evidence, and make retry after an unknown commit verify the terminal hold, log, audit and v2 event without a second debit.
3. Cover the remaining `reserved`, old-epoch, late-actual, BYOK `gateway_key_route`, released, no-hold, recovery, v1 event and mixed-scope branches enumerated in the [v369 coverage matrix](./C04-postgres-buyer-critical-write-coverage-v369.md). Update the privilege policy atomically with the complete writer switch and prove each branch with the full native schema and app transaction.

Until these are present, the existing `critical-writes.impl.ts` stays on its established default path. The v368 policy and helper remain review-only. No remote SQL, deployment, Provider call or production credential was used in this counterexample.
