# C04.6 Worker economic delivery scanner candidate (v350)

This is a **review-only, default-off runtime binding** for the v342 durable economic delivery proposal. The [scanner](../../../../packages/proxy/src/runtime/postgres-shared-earning-scanner.ts) is called from the proxy Worker's existing hourly `scheduled` entry point. The shipped Wrangler configuration omits `SHARED_EARNING_SCANNER_ENABLED`, `EARNING_DELIVERY_HYPERDRIVE` and `EARNING_CONSUMER_HYPERDRIVE`; its default invocation returns `disabled` before opening a connection.

The [Wrangler generator](../../../../scripts/deploy/gen-wrangler.mjs) adds these two proxy-only Hyperdrive bindings only when `DATABASE_DRIVER=postgres`, `HYPERDRIVE_ID`, `SHARED_EARNING_SCANNER_ENABLED=reviewed-v1`, `EARNING_DELIVERY_HYPERDRIVE_ID` and `EARNING_CONSUMER_HYPERDRIVE_ID` are supplied together. It rejects missing, malformed or reused Hyperdrive IDs, including collisions with enabled dispatch, fact and repair origins. The runtime also rejects absent or duplicate connection strings and unsupported URL overrides before opening a client. The PostgreSQL transactions verify the actual direct delivery and consumer `SESSION_USER` and database-user-sourced server deadlines; a URL or Hyperdrive ID alone does not prove server identity.

Each Cron run uses an invocation-private delivery client and at most one claimed event at a time. It calls v342 `claim_events(1, 300)` in a transaction, passes only the returned event ID to the separate v340/v343 consumer LOGIN, and calls marker-gated `ack_event(event_id, token)` only after the consumer transaction reports a confirmed commit. The loop admits at most 20 events and stops admitting claims after a 25-second monotonic budget. A zero-row claim can mean a completed-marker or dead-letter housekeeping row was processed before the next pending job. The scanner checks `pg_current_xact_id_if_assigned()` in the same transaction: an assigned transaction ID means the delivery function touched a due row and permits another scan after commit, capped at 20 housekeeping passes and the same admission budget. A read-only zero-row result stops immediately as `no_claim`, so a genuinely empty queue is not repeatedly polled. A concurrent lock can still make `no_claim` differ from a durable empty-queue certificate. An uncertain claim, consumer or ACK response stops the loop. The lease and immutable consumer marker allow a later invocation to reclaim or reconcile without a second seller credit. An expired unmarked lease eventually reaches the v342 dead-letter state after eight claims and requires audited manual requeue.

The Worker composes the delivery and consumer clients from separate Hyperdrive bindings, each with a one-connection postgres.js pool, and retires confirmed consumer clients after each event. All remaining invocation-private clients are retired at the end; a failed retirement is surfaced in logs and, if no earlier failure occurred, as a failed scheduled invocation. Retirement completion is not evidence that a physical Hyperdrive origin connection has closed. This scanner does not use or ACK a Cloudflare Queue message. The delivery and consumer bindings currently coexist with HTTP `fetch` in the same proxy Worker. Direct database-role checks guard against accidental role substitution; if the deployment threat model requires HTTP request code to have no access to seller-credit credentials, the scanner must run in a separate Worker with its own bindings.

- [Scanner unit tests](../../../../packages/proxy/src/runtime/postgres-shared-earning-scanner.test.mjs): **10/10 PASS**, including default-off, distinct Worker binding composition and cleanup, claim/consumer/ACK order, three lost-commit-response restart paths, wrong LOGIN, admission deadline, housekeeping progress and the bounded empty-scan distinction. Existing [single-event delivery tests](../../../../packages/proxy/src/runtime/postgres-shared-earning-delivery.test.mjs): **6/6 PASS**.
- [Wrangler generator tests](../../../../scripts/deploy/gen-wrangler.test.mjs): **15/15 PASS**. The two scanner cases verify proxy-only opt-in and rejection before writing generated configuration; the default case confirms scanner activation is absent.
- Proxy `npm run typecheck -w @octafuse/proxy`: **PASS**.
- [Owned PostgreSQL 18.6 fixture](../../../../scripts/db/cutover/postgres-shared-earning-scanner-v350.native.test.mjs): **7/7 stages PASS, cleanup PASS**. It installs formal PG73 and the review-only quote, dispatch, outbox, consumer and delivery proposals; creates synthetic economic events; denies ordinary runtime in the delivery and consumer positions; verifies expired-lease restart, lost ACK response and lost consumer response without double credit. The liveness negative puts a preconsumed marker job first and a pending job second; one Cron run completes both jobs, credits the second exactly once, then a genuinely empty scan stops without housekeeping retry. [Machine summary](./C04-postgres-shared-earning-scanner-v350-results.json) pins the SQL, runtime and fixture hashes.


## Remaining operational requirements

The existing hourly Cron and 20-event cap can process at most 20 events per hour in this candidate; production arrival rate, latency target, backlog alert threshold and scan cadence need an explicit capacity design. The v342 proposal remains outside formal migrations, and the local fixture does not exercise deployed Workers, Hyperdrive, Cloudflare scheduling, origin connection budgets, credential custody or production crash behavior. The v343 consumer wrapper and v2 economic producer must be installed and accepted before any v2 event reaches this scanner. Legacy writer shutdown, unknown-cost review, financial reconciliation, D1/MySQL parity, dead-letter operations and C04.G remain open. No cloud resource, production SQL or economic feature switch was changed.
