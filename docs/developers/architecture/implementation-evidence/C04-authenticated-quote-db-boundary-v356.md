# C04 authenticated quote at the DB admission boundary (v356)

2026-09-25. **Review-only design and first-phase local SQL.** The [v356 proposal](../../../../packages/core/migrations-proposals/postgres/authenticated-request-capability-login-v356.sql) and [owned PostgreSQL fixture](../../../../scripts/db/cutover/postgres-authenticated-request-capability-login-v356.native.test.mjs) establish a bearer-verified, one-request authentication capability. No application wiring, formal migration, production role provisioning, remote test, or deployment is changed here. C04.1–8/G remain open.

## Boundary observed in the current candidates

| Boundary | What it verifies | What it still accepts from its caller |
| --- | --- | --- |
| [v350 ordinary reserve](../../../../packages/core/migrations-proposals/postgres/budget-admission-login-v350.sql) | Direct admission `SESSION_USER`, active Key owned by the named user, budget epoch, account capacity, and reservation/counter consistency. | `request_id`, user/Key IDs, and any positive `p_reserved_micros` within the numeric range. It does not check possession of the Key secret, Key expiry, the chosen route, or a price quote. |
| [v351 Guardrail reserve](../../../../packages/core/migrations-proposals/postgres/guardrail-budget-admission-login-v351.sql) | Direct admission LOGIN, active unexpired Key and Workspace, configured intent set, period, capacity, and ledger consistency. | User/Key/request IDs, `p_reserved_micros`, and `p_settlement_basis`. Its `gateway_key_route` branch checks the Key's BYOK setting and a single Key-limit intent, but no selected private-BYOK route. |
| [v354 Chat proof](./C04-authenticated-chat-budget-proof-v354.md) and [v355 request owner](./C04-ordinary-budget-request-owner-v355.md) | The opt-in Worker proof derives a complete-plan ceiling for three dispatch permits and compares request-local auth, route, and settlement snapshots; the owner fixes IDs and checks direct database LOGINs. | The proof is not a DB-verifiable bearer or quote assertion. Chat does not open the v350/v351 owners, and the owner does not authenticate the caller's bearer or price inputs. |
| [v338 seller quote](./C04-postgres-shared-key-quote-supersession-v338.md) and [v339 attempt claim](./C04-postgres-shared-key-dispatch-quote-attempt-v339.md) | An append-only seller rate/version and a pre-send reference to the active shared Key quote. | `route_target_id` and request-log ID come from the claim caller. This is not a buyer price, complete fallback-plan ceiling, bearer proof, or evidence of physical egress. |
| [v356 request capability](../../../../packages/core/migrations-proposals/postgres/authenticated-request-capability-login-v356.sql) | A separate direct issuer LOGIN passes the actual bearer to PostgreSQL. PostgreSQL hashes it, requires an active unexpired modern `key_hash`/`hashref` pair and matching personal-Workspace owner, and captures the current Key/user/Workspace, user budget epoch, and Key limit epoch. A separate direct claim LOGIN can consume the returned random capability once; only its SHA-256 verifier is stored. | The caller supplies the request ID and body digest. Organization workspaces are outside this first phase. There is no route or price quote, budget amount, financial reservation, or dispatch grant. A successful claim must never be treated as permission to send. |

The function-only LOGIN usefully removes raw budget DML, but `EXECUTE` is itself a financial capability. Anyone who obtains that LOGIN could ask v350/v351 to hold one micro for a valid Key/user pair, regardless of the actual priced request. For a Key with `include_byok_in_limit`, v351 can also accept a caller's `gateway_key_route` choice without knowing whether the dispatched route is private BYOK. These are **latent admission-contract gaps**, not a demonstrated external exploit in the current default-off path: the owners are not opened by Chat or shipped Worker configuration.

## First-phase v356 native evidence

The [PG18.6 report](./C04-authenticated-request-capability-v356-report.json) is **PASS with cleanup PASS** over 11 stages on a freshly created loopback cluster containing formal PG73 and the current runtime grants. Installation rejects a missing `cinatoken.request_capability_login_activation=reviewed-v1`, an issuer with raw Key `SELECT`, or a claimant with unrelated function `EXECUTE`, leaving no partial table. Installation shares the legacy runtime grant advisory lock; a concurrent grant rerun waits for installation and then rejects before broad regrant. The issuer and claimant have distinct `NOINHERIT` direct LOGINs, only their respective `SECURITY DEFINER` function, no raw table DML or Key reads, and no right to call each other's function. The fixture proves that a supplied hash, wrong bearer, Management-namespace bearer in a malformed Key row, legacy plaintext row, foreign personal-Workspace owner, or expired Key cannot issue; only the actual inference bearer matching the current `sha256:` plus `hashref:` Key pair does. The stored one-request verifier is a hash, replay is rejected, and simultaneous claims yield one winner. Migrator-owned invalidation triggers on security-sensitive Key/user/Workspace changes permanently reject a capability after a revoke/reactivate ABA. Current-row and epoch checks provide a second gate. Real row-lock waits that cross the capability or Key deadline fail closed, and a held lock times out after two seconds. Neither function accepts a numeric budget argument, and the capability table contains no amount column.

The issuer's body digest is still caller asserted: PostgreSQL cannot independently reconstruct the HTTP bytes. The capability is deliberately an **authentication artifact only**. It does not call v350/v351, derive a ceiling, reserve funds, authorize a route, bind a seller quote, or grant a fetch. Sending after `claimed` would violate this design. The raw bearer crosses the DB connection as a bound parameter; production TLS, statement logging, and credential separation remain to be proved. Legacy Key backfill and an organization-membership contract are required before this strict issuer could cover all valid Keys. Trigger invalidation filters to unexpired, still-issued rows through `(identity, expires_at)` partial indexes, but capability rows and their index entries persist indefinitely until an owned retention/purge job is designed. Trigger scan/write capacity under production Key/user/Workspace churn is unmeasured; it remains a cutover gate. The fixture is Windows PG18.6 only; D1/MySQL parity and Linux CI remain open.

## Proposed phased contract

1. **Create a separately authorized request quote.** A quote issuer with credentials unavailable to the budget-admission LOGIN verifies possession of the actual Gateway Key bearer against the current Key record, including status, expiry, owner, Workspace, and budget epoch. It resolves the complete eligible fallback plan from authoritative route and price versions and writes one insert-only request quote, returning an unguessable, one-request admission capability whose verifier alone is stored by the DB. The record binds a unique request ID, authenticated Key/user/Workspace, normalized request-body digest, candidate model/index, each permitted target and credential class/identity, endpoint price and tier/speed/override, charged factors, buyer billing mode, currency/unit, and eligible shared-Key identities. The actual seller `transition_id`/`quote_version_id` is fixed at the per-attempt grant. The quote records the ceiling algorithm version, finite per-route token/request limits, three-permit cap, and derived integer-micro ordinary, charged-Guardrail, and BYOK Key-limit ceilings. An admission-supplied Key ID, bearer *hash*, session GUC, or unsigned JSON is not proof of bearer possession. The quote issuer must calculate from trusted inputs; the admission LOGIN cannot mint, alter, or backdate a quote. A signed envelope is equivalent only if PostgreSQL verifies its signature and freshness with a key unavailable to the admission caller.
2. **Replace numeric-argument reserve with quote consumption.** A successor DB function takes only the request/quote reference and issuer-issued capability, locks the quote plus current Key, user, and affected budget rows, and checks capability validity, exact idempotent replay, issuer authority, request identity, validity window, revocation/epoch, quote and calculation versions, and complete plan coverage. It derives the held amounts and applicable intents from the immutable quote, using checked integer arithmetic; no admission caller selects an amount or `settlement_basis`. The first version should reserve the full paid-capable plan ceiling before any send, including independently billable failed attempts. If a later version admits BYOK first and extends for a paid fallback, that extension must be monotonic and committed **before** the paid send. A proven free or BYOK-only request needs an explicit quote state, not a caller-chosen zero or one-micro hold. A partial or unknown commit does not grant dispatch.
3. **Bind every dispatch attempt to that quote.** Before fetch, a DB grant consumes one of the quote's at most three permits and records an immutable `(request_id, quote_id, attempt_id, selected_target, credential_identity, billing_basis)` tuple. It requires the target and credential to be in the quoted plan, the required ordinary/Guardrail/Key holds to be committed, and the basis to follow the selected route; a paid route cannot use `gateway_key_route`. Shared-Key claim and grant must agree on request, target, Key, owner, and active seller quote version under the same request lock. A changed route/price/owner or revoked quote before grant requires rejection and a new authenticated quote; a previously granted attempt retains its immutable financial reference. Fetch may start only after grant COMMIT acknowledgement. The egress credential holder must check the grant against the actual target; while the same Worker can fetch with an unrestricted provider secret, PostgreSQL alone cannot prove which route was physically sent.
4. **Carry the proof through settlement and recovery.** Buyer critical write and typed outbox must reference the same authenticated quote, reservation, dispatch grants, selected route, and each attempt's seller quote/fact. Database constraints reject missing or mismatched references and duplicate economic keys. Lost COMMIT acknowledgement stops new sends and is resolved by exact request/attempt lookup; it is not answered by replaying inference. Unobserved transport, earlier failed attempts, supplier cost, and late actual usage remain `unknown` until separately evidenced and adjusted under the C04/C05 policy.

## Evidence required before any cutover

An owned PostgreSQL fixture must show that direct admission LOGIN calls cannot substitute a one-micro hold, another user's active Key, a replayed request quote, an unquoted or repriced target, a fourth attempt, or `gateway_key_route` on a paid route. Race tests must cover Key revocation/expiry, quote and seller-price changes, simultaneous admission, and unknown COMMIT outcomes. A real Chat/credential-holder integration must show zero upstream sends on every failed or unconfirmed proof/grant and exact quote/grant references in buyer log and outbox. Separate production credential isolation, formal migrations, Worker/Hyperdrive behavior, D1/MySQL parity, and invoice/unknown reconciliation remain unproved by this note or the existing local fixtures.
