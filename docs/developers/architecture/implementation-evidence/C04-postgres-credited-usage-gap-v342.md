# C04.7 PostgreSQL credited usage gap and rebuild design (v342, review only)

The [read-only per-key audit](../../../../packages/core/migrations-proposals/postgres/shared-key-credited-usage-gap-audit.sql) compares the current `shared_keys` usage fields with **both** immutable credit sources: legacy `shared_key_earnings` and v340 `cinatoken_economic_consumer.shared_key_attempt_consumptions` where `decision='credited'`. It reports pending decisions separately, a cross-source request-log conflict, and credited details whose seller snapshot differs from the Key's current owner. It changes no database object or runtime path.

## Observed gap

The [PostgreSQL repository rebuild](../../../../packages/core/src/db/postgres/portal-marketplace.impl.ts) and the review-only legacy repair proposal aggregate only `shared_key_earnings`. The v340 consumer credits the seller account and appends a consumption detail, but does not update `shared_keys.served_input_tokens`, `served_output_tokens`, `earned_total`, or `last_used_at`. A failure or missing follow-up after seller credit therefore leaves those fields stale. A later legacy-only rebuild can overwrite any separately added economic amount with the legacy-only total. An incremental update after credit is insufficient unless its durable work record is committed in the credit transaction.

The [native PG18.6 fixture](../../../../scripts/db/cutover/postgres-shared-key-credited-usage-gap.native.test.mjs) loaded the exact 73 formal migrations plus the v338 quote, v339 dispatch/outbox, and v340 consumer proposals. The pinned [result](./C04-postgres-credited-usage-gap-v342-results.json) has **10/10 stages PASS and cleanup PASS**. One legacy credit of `2.000000`, one economic credit of `5.625000`, and one `pending_manual` attempt yielded `7.625000` credited detail while the Key still displayed `0.000000`. Replaying the repository's legacy aggregate set it to `2.000000`, still short by `5.625000`. Two concurrent further economic credits raised credited detail to `18.875000` while the Key stayed at `2.000000`. A reviewed owner transfer kept all four earlier credited rows attributed to the former seller snapshot. The fixture also confirmed the ordinary runtime role cannot read private economic details. Source SHA-256 pins are in the result JSON.

## Write-side proposal for a separately reviewed change

1. Make a private, append-only contribution table with `(source_kind, source_id)` as the idempotency key. `legacy` uses `shared_key_earnings.id`; `economic_attempt` uses the globally unique `attempt_id` while retaining `event_id` and `request_log_id` for audit. Each contribution copies `shared_key_id`, **source seller_user_id**, token counts, net micros, and credit time. Legacy amount conversion uses exact `numeric × 1000000`; economic uses `net_micros`. Store totals as `numeric` with explicit bounds before any API number conversion. A cross-source request-log overlap must fail closed rather than sum twice; the v339 guards currently prevent one on the normal path.
2. Install source `AFTER INSERT` triggers under source-table write locks. The economic trigger accepts only `decision='credited'`, including confirmed zero, and uses `processed_at`; the legacy trigger uses `created_at`. A pending decision is recorded in a separate pending metric if needed, but contributes **zero** to credited token and earning totals and cannot later be rewritten. A future adjustment event needs its own contribution identity. The trigger inserts the contribution and updates a canonical summary keyed by `(shared_key_id, seller_user_id)` in the **same transaction** as the immutable detail and seller credit. Any summary error aborts the credit; a lost commit ACK is resolved by the source and contribution unique keys. Account balance, contribution, and summary then commit or roll back together.
3. Backfill pre-activation history in bounded batches from each source, ordered by a stable source identity and resumed with a durable `(source_kind, last_source_id)` cursor. Use `INSERT ... ON CONFLICT` only after verifying the existing contribution equals the immutable source. Trigger installation must finish before the backfill starts: source-table DDL locks wait for older writers, and every later writer is captured by the trigger even if its random ID sorts below the backfill cursor or commits after a page scan. Backfill insertion and summary increment share one transaction. A batch cap and measured index plan are required; the existing legacy `(shared_key_id) INCLUDE (...)` proposal does not index the economic source. No all-history aggregate belongs in a request or a short-timeout worker call.
4. Keep the canonical summary outside `shared_keys` until the readers and legacy writers are cut over together. Existing `rebuildSharedKeyUsageFromEarnings`, direct `updateSharedKeyUsage`, and legacy repair functions can overwrite the four `shared_keys` fields. A future migration must either remove their write authority and mirror the canonical summary safely, or switch every seller statistics reader to the new table. Key-level totals across multiple owners must not be presented as earnings of the current owner. The seller snapshot, not a join to mutable `shared_keys.seller_user_id`, determines attribution. `last_used_at` in this credited projection means the maximum source credit timestamp, not the upstream request's observed time.
5. Activation must be a single direct-migrator transaction with an explicit local review flag and exact PG73 plus v338/v339/v340 source and guard preflight. Reject altered source ownership, missing immutable triggers, RLS, unexpected role membership, hostile default ACLs, or any direct runtime table access. Definer triggers must use a fixed `pg_catalog,pg_temp` search path and no broadly executable function. Seed and verify all historical rows, source counts, seller attribution, totals, and cross-source overlaps before a reader cutover. The existing v340 dedicated consumer keeps only its narrowly granted `EXECUTE` right. No production worker or route is activated by this v342 audit.

The current audit intentionally scans one Key's full history within a `REPEATABLE READ READ ONLY` snapshot and is suitable for targeted review with a statement timeout. It is not a large-history production rebuild. The contribution schema, trigger lock order, bounded backfill, integrity checks, exact grants, and reader cutover need a new native concurrency fixture before C04.7 can be considered closed.

Run the fixture with `GATEWAY_NATIVE_PG_BIN` set to the owned local PostgreSQL 18.6 `bin` directory:

```powershell
node --test scripts/db/cutover/postgres-shared-key-credited-usage-gap.native.test.mjs
```

On Windows, `pg_ctl` required execution outside the filesystem sandbox to create its restricted token. The fixture uses only a fresh loopback cluster, confirms its data-directory identity, and cleans it up after the run.
