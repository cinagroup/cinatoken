# C04 v345: bounded buyer receipt maintenance candidate

Status: **review only, default off**. [The maintenance proposal](../../../../packages/core/migrations-proposals/postgres/shared-key-buyer-budget-receipt-maintenance.sql) installs after the v344 buyer receipt in a direct migrator transaction. It adds no formal migration, scheduler, retention period, runtime permission, or production activation.

The v344 `(xid8,user_id)` receipt is needed to verify the current transaction's economic events. Left alone, it gains rows as user budget fields change. The v345 expansion adds nullable `first_seen_at` and sets a default for new rows without rewriting all old rows, following [PostgreSQL 18 ALTER TABLE behavior](https://www.postgresql.org/docs/18/sql-altertable.html). A bounded migrator function timestamps up to 1,000 old rows per call at the time they enter the maintenance policy. Another function accepts an explicit cutoff and deletes at most 1,000 rows per call only when `first_seen_at < cutoff` **and** `xact_id < pg_snapshot_xmin(pg_current_snapshot())`. PostgreSQL defines that snapshot minimum as the oldest still-active transaction ID; lower IDs have completed or rolled back. [PostgreSQL 18 transaction snapshot documentation](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-TXID-SNAPSHOT) supports that ordering. Rows locked by another writer are skipped. Both functions require the direct migrator LOGIN, READ COMMITTED, and an exact run-marker value; the runtime LOGIN cannot execute them. Operators should use `SET LOCAL` for each run, but the function cannot distinguish it from a session-level `SET`, so this marker is an operator guard rather than transaction-scoped authorization ([PostgreSQL SET](https://www.postgresql.org/docs/18/sql-set.html)).

The [owned PostgreSQL 18.6 fixture](../../../../scripts/db/cutover/postgres-shared-key-buyer-budget-receipt-v2.native.test.mjs) passed **47/47 stages, cleanup PASS**. Eight maintenance stages exercise the install marker, rejection of a runtime column-level grant, ACL postflight, runtime denial, bounded old-row backfill, a locked remaining row that makes a page return zero until retried, default time on new receipts, an open older transaction preventing deletion of newer committed receipts, and bounded deletion after that transaction completes. Seven later stages test the separate [v346 delivery integration](./C04-postgres-v2-economic-delivery-integration-v346.md). Its [machine report](./C04-buyer-budget-receipt-maintenance-v345-results.json) pins maintenance SQL SHA-256 `107f4109e905e346fbd8c2b88c47f3b8068237d854e2033a4dbd2e45eb0c4f67` and fixture SHA-256 `934b996e899f904530076913dfadd897e659943e67aba36c9a4e4679cad8ac3a`.

This proves the local pruning rule, not a retention policy or production-scale operation. `first_seen_at` records insertion or backfill time, not commit time. A long transaction could insert a receipt, commit after the cutoff, and become eligible immediately after commit; a policy requiring a minimum duration **after settlement commit** needs another verified time source. `SKIP LOCKED` also means a zero-row page can coexist with eligible rows locked by another transaction, so completion requires an independent remaining-row census and retries. A reviewed financial/audit retention cutoff, scheduling identity, monitoring, index and scan cost, `ACCESS EXCLUSIVE` install lock window, old-row backfill duration, per-run authorization, and preservation of admission/event evidence remain open. No receipt rows were pruned outside the disposable test cluster. C04.3 and C04.G remain unchecked.

The later [v346 retention companion](./C04-buyer-budget-receipt-retention-v346.md) tests a conservative post-finalization observation time and the required partial indexes; retention duration and production operation remain undecided.
