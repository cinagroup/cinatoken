## 能力与持有边界

独立 `usage-recovery-fencing-worker.ts` 保留无参命名 `UsageRecovery.run()` 和固定 HTTP 404。仅有 staging D1 与 8 个原参数，没有服务调用、模型、KMS、公开触发器、租户或 SQL RPC 参数。原消费者文件、默认关闭配置、生产代码、Core、SQL 和账务算法均未更改。

`withRecoveryFencingProbe` 在调用内构造，不执行 I/O。所有探针查询、等待和真实 batch 仍在原 `createUsageRecoveryHost` 的 waitUntil 与逻辑容量持有期内；disabled 或 waitUntil 登记失败时，不做探针查询。模块内仍只保留原 host 的数字/配置状态，不保留租户、数据库或请求。

探针仅检查关键记账 batch。固定控制键 `c02_recovery_fencing_control_v1` 必须具有精确 description；SQL 在返回 Worker 前将值限制为最多 190 字节，只解析有限的 `before-release` 合同，不解释配置 JSON、SQL 或可变等待时长。无控制行直接走原生 batch；无日志的 batch 不读取控制行；坏控制行拒绝执行。

合法控制只能命中指定合成 user/key/workspace，随后仍需精确随机 probe 的 armed 行并一次性 CAS。其他租户不暂停；缺失 armed 行、外来 statement、歧义多日志 batch 和 session 绕过均拒绝。复用原真实 D1 batch 暂停器，固定最多 20 次 × 500 ms，丢失所有权或未释放会失败，不伪造提交成功。

控制行仅用于操作者布置单个实验，不是认证机制。只有已经隔离且有权限的 staging 操作者可以写入；RPC 不增加写入能力。控制行必须在该探针收尾后精确移除，重试使用新探针或先解除控制，不能复用已经消费的 armed 行。

## 真实线上实验的下一步

在重新核验基线、封闭入口、Access、独立 D1、预算与生产只读指纹后，才发布已锁定的两个候选。Gateway 用 v1.66 的 5 秒租约/40 次轮询；消费者保留 30 秒租约/20 次轮询和 64 MiB 实验逻辑分配。任何一个均不是已验收的物理内存或生产租约建议。

单个场景的有限顺序：

1. 为一个合成请求布置旧生产者与新消费者的不同随机探针和精确控制行，发送一次普通 Images 请求。
2. 观察旧生产者持有未提交事务；等待真实 D1 时钟证明旧租约过期，不修改任何租约/任务时间。
3. 异步调用受保护、无参的恢复控制入口，保持调用在途；观察新消费者已认领 revision/token 且暂停、尚无日志/回执。
4. CAS 释放旧执行者，验证真实租约错误与账务/新租约不变，再 CAS 释放新消费者并完整等待 RPC 收尾。
5. 精确解除控制，复查一次记账与不可变快照、重复 RPC 无变化，关闭入口、回收身份并清理样本。

若无法在有界等待内建立该时序，记录失败并收尾，不能把“新消费者先提交后的重复键失败”当成租约隔离通过，也不能扩大轮询或篡改时钟来制造通过。对尚在途的消费者，不提前删除其探针/财务数据；先释放或待有限超时并核验终态。
