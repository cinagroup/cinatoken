## 1. 风险与实现

现有分段解析器对字符串保留片段，但数字仍经 TextParts 汇集、整值拼接和 JSON.parse。单个数字就能占满 50 MiB 入口或 32 MiB 普通响应，无论最终数值是 1、负零或溢出，原实现仍保留并合并全部数字文本。只限制字符串形式的 n 不解决原生 JSON 数字的分配。

[JsonScalar](../../../../packages/proxy/src/services/egress/json-scalar.ts)逐段检查 JSON 数字及 true/false/null 的词法状态；保留最多 1,024 位非前导零有效数字，以及小数位数、有效位数、符号、指数和非零尾部标记。最终构造有界的十进制科学计数文本，交给原生 Number 舍入；不自行用浮点乘除重建数值。全零值保留正/负零。指数累计受已执行的原始输入字节预算加安全余量约束；足够大的指数不可能被较短的尾数抵消回有限范围，因而可饱和计数，而不是保存任意长指数。

有效位截断依据 binary64 舍入边界的有限十进制长度；[Google double-conversion 的实现](https://github.com/google/double-conversion/blob/master/double-conversion/strtod.cc)使用 780 位的保守边界并保留非零尾部信息。这里保留 1,024 位余量，另加一位尾部标记。词法状态机是本项目实现，原生 Number 仍是舍入执行者；不是仅凭“保留 17 位通常足够”来截断计费数据。

[分段解析器](../../../../packages/proxy/src/services/egress/segmented-json-response.ts)不再把裸标量写入字符串汇集器，标量完成后立即释放扫描器。字符串转义仍用有界原生 JSON.parse，完整对象/数组语法仍由紧凑结构的原生 JSON.parse 验证。完整 EOF、字节/结构预算、重复键最终值、安全属性恢复、错误预览与取消清理不变。非法标量即使提前识别，也不绕过后续字节/节点限制和 EOF 合同。

实际调用者为 Images JSON 生成入口与普通非 SSE Images 上游读取。**不覆盖 SSE 事件、multipart 内嵌 JSON、其他模态、Admin 或直接调用原生 JSON.parse 的代码**。50/32 MiB 容量和合法数字的原生值合同保持；1,024 位是内部保留量，不是公开输入位数上限，不是对普通字符串的额外限制。

Cloudflare Workers 最佳实践技能推动了检查“分块后整值拼接”的剩余分配及终止清理，参考 [官方指南](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/)。最新 types registry 获取失败，按技能回退核对本机 Workers types 5.20260829.1 与 Wrangler schema；兼容日期、flags、bindings 和依赖不变。

## 3. 内存与 CPU 权衡

[原始结果](./C02-json-numeric-memory.json)来自 [独立脚本](../../../../packages/proxy/scripts/measure-json-numeric-memory.mjs)，每组完整读取 50 MiB 输入，使用独立 Node v24.14.1 / Windows 子进程、离散采样和显式 GC。整段文本 + 原生 JSON.parse 是**分配对照，不是 v1.32 的历史解析器**；前版还有结构扫描与分段还原，不能把此表当作直接版本性能对比。

| 内容 | 整段文本对照堆增量峰值 | 当前分段路径堆增量峰值 | 当前解析后 GC 增量 | 当前原生转换最大输入 |
| --- | ---: | ---: | ---: | ---: |
| 溢出整数 | 102.84 MiB | 6.21 MiB | 2.30 MiB | Number 1,033 字符 |
| 长尾数/指数抵消为 1 | 102.96 MiB | 6.21 MiB | 2.29 MiB | Number 1,030 字符 |
| 极长指数的 -0 | 110.65 MiB | 6.17 MiB | 2.29 MiB | 仅引用索引 1 字符 |
| 尾部非法字符 | 110.65 MiB | 6.21 MiB | 2.36 MiB | 不调用数值转换 |

当前紧凑结构 JSON.parse 最大仅 7 字符；非法组在结构还原前拒绝。测量的 heapUsed 是相对各自进程基线增量，不是整个进程 RSS 或 Workers 可用内存。观察点不是连续峰值，GC 不在应用逻辑中。

**不能宣称整体性能提升**：此测量的当前路径约 654–759 ms，原生整段文本对照约 166–213 ms。当前实现包含结构扫描和逐字符词法处理，内存改善伴随 CPU 成本；它也不是前版的直接计时对照。没有 Node 22、Workers、真实网络或多请求负载证据。
