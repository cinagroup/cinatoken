## Transaction and window-creation protocol

The proposed caller first inserts its append-only request log, calls `settle_legacy_buyer_windowed_v371(request_id, reason)` on **the same direct buyer LOGIN and outer transaction**, then writes its audit and v2 economic event before COMMIT. The SQL checks that the log, ordinary hold, API key, user and Workspace agree; requires a non-BYOK success log with a nonnegative `budget_charged_micros` equal to six-decimal `charged_cost`; and obtains locks in this order:

1. Request advisory lock `pg_advisory_xact_lock(348, hashtext(request_id))`.
2. Existing log row and API key `FOR SHARE`, then ordinary user account `FOR UPDATE`.
3. Both reservation tables in `ROW EXCLUSIVE`, then the entire Guardrail window table in `SHARE ROW EXCLUSIVE`.
4. The exact v368 held transition on the same transaction, followed by an UPDATE for applicable unreserved user, API-key and canonical Workspace windows. A matching `reserved`, `dispatched`, `settled` or `expired` request reservation excludes a window from the unreserved UPDATE, so held windows receive only their v368 transition.

The whole-table window lock conflicts with every window `INSERT`, `UPDATE` and `DELETE` and persists until the **outer** COMMIT or ROLLBACK. A creator that commits before the lock is visible to the buyer's read-committed statement and is charged by v371. A creator after the lock waits for the buyer transaction to finish; a `BEFORE INSERT` trigger then seeds the new window from committed request logs and excludes matching held reservations. The trigger rejects noncanonical Workspace IDs and positive historical log amounts whose `budget_charged_micros` disagrees with `charged_cost`. The SQL revokes direct buyer EXECUTE on v368, grants only v371, and leaves buyer raw window UPDATE denied. It has an installation opt-in GUC and a pinned v368 function body.

The full PG73 native fixture observed both block directions through `pg_blocking_pids`, with a held user window, an applicable Workspace window, an applicable API-key window and an unrelated user window. It found one settled micro in the held window, one unreserved micro in each applicable unheld window, and zero in the unrelated window. Separate cases show outer rollback removes the log and every financial transition, terminal replay rejects without another debit, wrong-charge and BYOK logs reject before writes, workspace-scope spoof and mismatched positive historical charge reject, and a contended window-table lock times out after two seconds with the whole buyer transaction rolled back. This is a transaction mechanics proof, not an idempotent commit-unknown recovery protocol.

## Remaining gates and cost

- The fixture uses all 73 formal PostgreSQL migrations and the exact v368 held function body, but installs a minimal v362 grant table rather than the full v351–v368 proposal chain. It does not run the actual v2 economic producer or application critical writer in this case. Their composition and positive rights still need full-schema proposal-chain proof.
- The trigger's historical source follows the existing v351/v355 `COALESCE(budget_charged_micros, rounded charged_cost)` policy for older logs. It rejects internally inconsistent positive amounts, but a consistent fabricated log or legacy log without a trusted buyer fact remains possible. A buyer with raw log INSERT can also commit a log without calling v371. Before activation, financial closure must bind the amount, final result, log, hold transition, audit and v2 event to an authenticated immutable fact and enforce all-or-none buyer writes.
- The global `SHARE ROW EXCLUSIVE` window-table lock serializes window creation and updates across unrelated requests. It can lower throughput and form a cycle with a creator that holds a window table write lock and later requests the buyer's account lock. The function bounds lock waits to two seconds and rolls back on timeout. Any operational retry must restart the **whole** buyer transaction only after its prior COMMIT outcome is known; hidden retry of the SQL function is unsafe. Production-scale capacity, fairness and deadlock frequency remain unmeasured.
- The v368 held function still covers only non-grant, current-epoch, charged-basis, active held `actual` settlement. The `reserved`, old-epoch, late-actual, BYOK route basis, released, no-hold, recovery, mixed event-version and idempotent replay paths in the [v369 coverage matrix](./C04-postgres-buyer-critical-write-coverage-v369.md) still need reviewed successors. Complete-text grant-linked closure, Provider bill validation, Worker/Hyperdrive acknowledgement and coordinated privilege cutover remain open.

No formal migration, remote database, deployed Worker, Provider or production credential was changed.
