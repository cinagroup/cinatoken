# C04 OpenRouter generation cost source candidate (v372)

2026-09-25. **Review only.** The [read-only candidate inspector](../../../../scripts/db/cutover/openrouter-generation-cost-candidate-v372.mjs) and its [deterministic tests](../../../../scripts/db/cutover/openrouter-generation-cost-candidate-v372.test.mjs) add no route activation, database write, `provider_bill`, buyer debit or zero-charge decision. No provider API or paid inference call was made.

## Official source and bounded conclusion

OpenRouter documents an authenticated [`GET /api/v1/generation?id=...`](https://openrouter.ai/docs/api/api-reference/generations/get-generation) response with a generation ID, request ID, `external_user`, model, `is_byok` and `total_cost`. The [Chat API](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request) accepts a `user` field, and [response caching documentation](https://openrouter.ai/docs/guides/features/response-caching) shows an individual Chat generation ID in the response and says `X-Generation-Id` is present on every response, cached or not. OpenRouter also documents a management-key [`GET /api/v1/keys/:hash`](https://openrouter.ai/docs/api/api-reference/api-keys/get-key) returning the sending key's hash and workspace ID. These are specific, itemized source and account signals that the generic v366 JSON lacks.

The generation endpoint's public contract does **not** state when `total_cost` becomes final, how later adjustments are represented, a complete zero-charge certificate, or whether a separate management key can read a generation created with the sending key. It does not place a workspace or sending API-key hash in the generation record. Therefore the inspector returns only `positive_cost_candidate` or `zero_unproven`, always with `financialAuthority: false`. A local mock 200 is evidence about our parser and fences, not proof that OpenRouter will permit the cross-key lookup or that a supplier amount is final.

## Candidate source contract

The inspector requires a trusted registry pin for one OpenRouter Chat route: internal provider, route, Endpoint, credential, model, OpenRouter workspace ID and sending key hash. It rejects a grant whose persisted identity differs, whose custody/send-start is not committed, or whose upstream URL digest is not exactly `https://openrouter.ai/api/v1/chat/completions`. A separate management key must differ from the sending key. The adapter first performs the management-key GET for the pinned sending key and verifies the reported workspace and enabled status. Only then does it GET the observed generation ID on the fixed OpenRouter origin. Both calls use `GET`, a 5-second timeout, `redirect: error`, no cache, JSON content type and a 16 KiB body cap. The response must match the observed generation ID and request ID, pinned model, Chat API type, non-BYOK mode and a server-prepared per-attempt `user` value echoed as `external_user`. The inspector retains SHA-256 digests of the exact fetched JSON bytes, and does not convert the floating JSON cost to money units or call v366's bill writer.

The present v360/v365 path has no provisioned OpenRouter account pin, sending-key hash in the grant, preallocated per-attempt `user` field or durable generation-ID observation. Thus it cannot supply the inspector's trusted inputs today. The `user`/`external_user` association is inferred from the official field names and examples, not an explicit guarantee that OpenRouter echoes it exactly. A future account-specific staging check must establish that behavior before using it as correlation evidence. Reusing an end-user-controlled `user` value would fail the contract.

Even when every local check passes, a generation ID observed by the holder is only a lookup lead. The authenticated source response confirms a generation with matching metadata; it does not prove that no other generation was charged for a lost response, hidden retry, or provider-side fanout. This path never treats a 404, timeout, empty record, reported zero, or aggregate Activity/Analytics query as a zero bill.

## Next gate

1. Provision one **actual** OpenRouter-owned route and workspace, separate sending and management credentials, and an immutable registry pin for the exact Endpoint, model and sending-key hash. Verify with read-only calls that the management key can retrieve a generation created by the sending key in that workspace. Record the real response schema and key/account behavior; a 403 or cross-workspace result fails this candidate path.
2. Before quote, generate a unique correlation value, freeze it into the exact outbound Chat body using a provider-documented field, and persist it with the grant and send-start. Capture the response generation ID and request ID as holder observations. Exercise one physical POST, lost response, cancellation, redirect refusal and no hidden retry in a controlled account. Do not infer a missing generation ID means no charge.
3. Obtain a provider source contract or empirical signed statement for `total_cost` currency, finality, zero coverage, late adjustments and per-attempt completeness. If unavailable, keep cost unresolved under the [v371 authority boundary](./C04-provider-bill-source-authority-v371.md). A successor verified-source table and resolver must store the independent source record and apply its own idempotency, audit and adjustment policy before any financial close.
