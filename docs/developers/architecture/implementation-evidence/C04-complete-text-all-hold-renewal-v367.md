# C04 v367 review-only all-hold renewal

2026-09-25. This is an owned PostgreSQL 18.6 proposal and local proof, **not** an activated migration, live Worker, durable recovery path, or C04 acceptance.

## Contract

[`complete-text-all-hold-renewal-v367.sql`](../../../../packages/core/migrations-proposals/postgres/complete-text-all-hold-renewal-v367.sql) adds a direct `NOINHERIT` renewal LOGIN with only one `EXECUTE` grant. The call binds the immutable v362 grant, v365 holder run and send-start, and the expected epoch. A new append-only row records each committed successor epoch. The v362 grant remains `unknown`; its original 15-minute deadline and v365 epoch-1/send-start rows are not changed.

For a live renewal, the function takes the request advisory lock, then the account row, reservation-table `ROW EXCLUSIVE` lock, exact admitted reservation rows, and Guardrail window rows. It checks the v361 intent identities/count, finite versus source-proven unlimited ordinary budget, dispatched state, zero settlement, the exact previous deadline, and every active-reservation sum against its counter. After the last lock wait, server time must still precede the previous deadline. One transaction appends the new epoch and extends every exact ordinary and Guardrail hold to at most 15 minutes after that server-time check. Any mismatch or failed update rolls the whole transaction back. Even with zero physical reservations, an unlimited/zero-intent grant stays an unresolved `unknown` financial obligation.

The same installation transaction replaces the v366 reservation fence. It allows only an `expires_at`-only update from the isolated renewer session when a matching append row was written by that same transaction; it continues to reject other grant-linked reservation mutations. An identical replay returns `already_recorded` without a deadline, epoch claim or renewed egress authority. The holder may use a new deadline only after both COMMIT and connection-close acknowledgements. This SQL cannot observe those client-side acknowledgements.

## Activation blockers

- The current buyer LOGIN can directly change `users.budget_spent`, `users.budget_reserved_micros` and Guardrail window counters without updating a reservation. v349 grant reconciliation restores those rights. The existing buyer writer takes a reservation row before the account row, so coordinating its replacement with renewal's account-first order is required. A one-off revoke can break unrelated legacy settlement. This proposal is **non-activatable** until a request-scoped buyer writer and grant policy are cut over with native continuity proof.
- v362 grant admission obtains reservation and window table locks before its Guardrail window rows; the suspected v362/v365 table/window inversion is not present. The local v367 same-request race and v366 reaper/send-start races still do not establish a fleet-wide cross-request lock proof for renewal and the buyer writer.
- The v370 result-fact successor can record committed renewal epochs, and the v369 local holder stops on uncertain renewal. Neither PostgreSQL nor the local test proves an acknowledgement reached a deployed Worker; suspension, provider cancellation and long-stream recovery still need runtime proof. An uncertain renewal must stop at the previously acknowledged local deadline.
- A recovery scan and atomic result closer must retain unresolved expired grants and settle or release **all** ordinary and Guardrail holds together without reviving physical send. Independent provider billing evidence, rather than holder observation or HTTP status, must determine zero charge. D1/MySQL parity, Linux CI, production role grants and deployment are not proven here.

C04.1–8/G therefore stay open.
