# C04.6 durable economic event delivery proposal (v342)

This is a **review-only, default-off PostgreSQL proposal**. The [SQL](../../../../packages/core/migrations-proposals/postgres/shared-key-economic-delivery.sql) installs after the exact PG73 ledger and the v338 quote, v339 dispatch/outbox, and v340 snapshot consumer proposals. It requires a direct `cinatoken_gateway_migrator` transaction with `SET LOCAL cinatoken.shared_key_economic_delivery_activation = 'reviewed-v1'`. It adds no formal migration, Queue worker, scheduler, production credential, payout route or runtime grant.

## Durable delivery contract

An `AFTER INSERT` trigger inserts one delivery job keyed only by `event_id` in the same transaction as every immutable v339 economic event. A failed buyer/event transaction leaves neither event nor job. Installation locks the event and v340 consumption-marker tables, installs the trigger, then backfills all existing events without a timestamp watermark. A preexisting event with a committed v340 marker starts completed; all other preexisting events start pending. Concurrent source or consumer commits occur before the locked snapshot or wait until the installation transaction commits, so the trigger and backfill leave no gap.

The private job holds delivery state, due time, attempt count, recovery count, random claim token, visibility lease and a bounded failure code. It copies no buyer amount, token usage, provider cost, seller or quote data. Pending and expired-lease lanes each have a due-time index. `claim_events(limit, lease_seconds)` locks at most `limit` candidates from each lane with `SKIP LOCKED`, then processes at most `limit` total. `claim_event(event_id, lease_seconds)` provides the same state transition for one exact Queue event ID. Limits are 1–100 jobs and 5–300 seconds. A claim increments the attempt count and replaces its UUID token. A stale token cannot ACK or fail a newer lease.

The delivery LOGIN calls the separate v340 consumer by passing **only the event ID** through that consumer's own LOGIN. The v340 consumer atomically commits attempt decisions, seller ledger/balance changes and its immutable event marker. `ack_event(event_id, token)` requires that committed marker before setting the job completed; an ACK before consumer commit fails. A repeated ACK after completion returns `already_completed`. A lost consumer commit response is safe to retry because v340 uses the event marker and event row lock for idempotency. An expired lease can be claimed again, and concurrent consumers still serialize on that same event. `fail_event` also completes a job if the marker already exists, avoiding a false retry after a misleading transport error.

Failures without a marker return a pending job with exponential delay: 5, 10, 20, 40, 80, 160 or 320 seconds after claims 1–7. Claim 8 failure, or its later lease expiry, dead-letters the job. The separate recovery LOGIN can call `requeue_dead_letter(event_id, reason_code)` only for an unconsumed dead letter; it resets the attempt cycle and writes an append-only reason/actor audit row. If a consumer marker arrives after a last-lease dead letter, `reconcile_consumed_event(event_id)` can complete it with no token because the marker is the authoritative settlement proof.

For a Queue message, first call `claim_event`. A zero-row result is deliberately ambiguous: the job might be absent because its event has not committed, locked by another claimant, waiting for retry, already completed or dead-lettered. `inspect_event(event_id)` returns `absent`, `pending`, `leased`, `completed` or `dead_letter` with due/lease metadata. A Queue handler may acknowledge its message on `completed` (marker checked) or `dead_letter` (durably retained for manual recovery); otherwise it should retry at the due/lease time. The indexed scanner remains a backstop after any Queue ACK or lost Queue message.

The installer pins the exact 73 migration names, expected source owners/types, v339 event trigger bindings, v340 marker guard/function and dedicated role attributes. It rejects inherited broad data privileges and hostile default grant options. Postflight verifies the new trigger/function catalog, owner, `SECURITY DEFINER` search path and exact narrow ACL. Delivery and recovery logins cannot directly read or write the job, audit, economic event or consumer tables. Ordinary runtime cannot use the delivery schema. Recovery cannot claim or ACK; delivery cannot requeue dead letters. Every function also checks its direct `SESSION_USER` and READ COMMITTED isolation.

## Native evidence

The [owned PostgreSQL 18.6 fixture](../../../../scripts/db/cutover/postgres-shared-key-economic-delivery.native.test.mjs) installed PG73 and all proposal dependencies, then exercised **17/17 stages PASS with cleanup PASS**. The pinned [summary](./C04-postgres-economic-delivery-v342-results.json) and [full report](./C04-postgres-economic-delivery-v342-report.json) include source SHA-256 values. Cases cover default-off and migration drift, disabled v340 marker guard, hostile default ACL rollback, direct-role denials, pre-install backfill including a source transaction held open during installer startup, atomic event/job rollback, marker-gated ACK, lost ACK, concurrent `SKIP LOCKED` claims, exact Queue-ID claims, lease/token fencing, backoff, last-attempt dead letter, audited manual requeue, late commit after an empty scan, marker reconciliation after a dead-letter race, and a local event-ID runtime candidate using distinct delivery and seller-consumer LOGINs. Final assertions compare event/job counts and require every completed job to have a marker.

The [default-off local runtime candidate](../../../../packages/proxy/src/runtime/postgres-shared-earning-delivery.ts) claims exactly one Queue event ID, invokes the [dedicated seller consumer](../../../../packages/proxy/src/runtime/postgres-shared-earning-consumer.ts), then calls marker-gated `ack_event` after its COMMIT acknowledgement. It checks direct LOGIN identity and database-user-sourced server deadlines in the same PostgreSQL sessions, and keeps ambiguous clients locally reachable. A zero-row claim invokes `inspect_event`; no zero-row case is treated as a delivery success. Its [unit tests](../../../../packages/proxy/src/runtime/postgres-shared-earning-delivery.test.mjs) pass **6/6**, including lost claim, consumer and ACK commit responses. Every result remains `queueAckSafe: false`: no production Queue handler, physical connection-close proof, or cross-isolate capacity owner has been established.

## Remaining gates

No production Queue handler, scan scheduler, credentials, metrics, retention plan, or operational recovery UI is activated. The fixture uses synthetic PostgreSQL facts; it does not prove real Workers/Hyperdrive crash behavior or D1/MySQL parity. A future v2 buyer-debit event needs its own consumer guard and marker contract before delivery can be activated for that event type. The delivery layer never completes any event that the installed consumer has not marked. C04 and financial release gates remain open.
