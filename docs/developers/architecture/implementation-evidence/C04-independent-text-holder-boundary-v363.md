# C04 independent flat-text holder boundary (v363 design review)

2026-09-25. This is a design-only cutover map for the strict v360 PostgreSQL Chat subset. No holder, Service Binding, credential migration, physical send, formal SQL migration, or acceptance test is installed by this note. C04.1–8/G remain open.

## Current route and credential boundary

The real Chat handler captures its post-preset and post-Guardrail final body in [`chat.ts`](../../../../packages/proxy/src/routes/v1/chat.ts), then sends either a per-model candidate or one global candidate sequence through [`proxyChatCompletions`](../../../../packages/proxy/src/services/proxy.ts) and [`failoverDispatch`](../../../../packages/proxy/src/services/failover-dispatch.ts). The latter delegates admission to the driver's `beforeFetch` callback. [`dispatchOpenAiRoute`](../../../../packages/proxy/src/services/egress/openai-driver.ts) currently resolves the URL, constructs and freezes the JSON upload, resolves the provider secret, creates the bearer header, calls `beforeFetch`, then executes the physical `fetch`. It also parses the returned SSE or JSON response and owns usage and resource-completion signals.

The [`Worker storage composition`](../../../../packages/proxy/src/runtime/workers.ts) and [`Node composition`](../../../../packages/proxy/src/runtime/node.ts) both install `createEncryptedProvidersRepository` using `SHARED_KEY_ENCRYPTION_SECRET`. That [`repository wrapper`](../../../../packages/core/src/lib/provider-key-encryption.ts) decrypts a stored `enc:v2:` Provider API key before returning the row. [`model-router.ts`](../../../../packages/proxy/src/services/model-router.ts) copies the plaintext into `route.providerApiKey`; the OpenAI driver then uses it directly or derives an OAuth token. Consequently, the review-only [v361 gate](../../../../packages/proxy/src/services/chat-text-grant-egress-contract-v361.ts) rejects normal live encrypted Provider routes at its `enc:v2:` check, and hashing `route.providerApiKey` there would hash plaintext rather than the v360 manifest's ciphertext. The gateway also already has the decryption key and runtime database access. Moving only the `fetch` call to another module or Worker would not create an independent credential holder.

The route planner has a second dependency: [`computeRouteDataPolicySubjectFingerprintFromRows`](../../../../packages/core/src/route-data-policy.ts) includes a hash of the plaintext Provider credential. A gateway route DTO with only a credential ID needs a separately attested, non-secret eligibility result; simply blanking `provider.api_key` changes the fingerprint and breaks routing. The v359 source generation and v360 manifest can supply the database-side source fence, but their review-only contracts have not replaced this live route-planning check.

## Proposed private holder

Use a separate private Worker reached only through a `COMPLETE_TEXT_EGRESS` Service Binding. The gateway selects a candidate and sends a bounded internal request containing the quote/request IDs, attempt nonce, candidate index, route target ID, and `FinalChatQuoteInput.finalBodyUtf8`. It sends no upstream URL, Authorization header, plaintext/ciphertext credential, or authoritative wire digest. The final body is limited to 1 MiB; v360 stores its digest rather than its bytes, so the holder must recompute that digest and parse the v360 strict subset against the committed quote.

The holder loads the current route, endpoint, source generation, and credential through its own restricted database and secret/KMS authority. It resolves the actual URL and secret and constructs the outgoing body with the same `buildRouteRequestBody`, `applyVertexOpenAiModelPrefix`, and `ensureOpenAiStreamIncludesUsage` steps used by the OpenAI driver. It freezes and hashes **its own** encoded upload, URL, and effective bearer. It submits that claim to [v362's attempt-grant function](../../../../packages/core/migrations-proposals/postgres/complete-text-attempt-grant-v362.sql) using a dedicated direct LOGIN and waits for both transaction COMMIT and connection-close acknowledgement. `grant_recorded` is only an in-transaction result; an unknown acknowledgement consumes the nonce and forbids sending. The holder verifies grant expiry and current source again at the physical send boundary, then makes one `POST` with `redirect: 'error'`. It never returns the secret or an arbitrary upstream-request capability to the gateway.

The holder returns the raw streaming provider `Response` over the binding. The gateway retains the existing Chat SSE/JSON normalization, usage collection, client cancellation, and request logging after the transport branch of `dispatchOpenAiRoute` is factored. Provider upload EOF, cancellation, fetch errors, response headers, and unknown outcomes must be recorded by the holder; completion of the gateway-to-holder request is not evidence of provider delivery. A holder crash after grant or during `fetch` leaves the v362 `unknown` obligation for recovery. The current v362 schema has no resolver or long-stream lease renewal, so it cannot yet complete that recovery or safely settle late provider bills.

## Trust and cutover requirements

- Give the holder the granter LOGIN, provider credential read authority, and the credential unwrap/KMS capability. The gateway receives only a secretless route view and a private Service Binding; its runtime role must lose direct Provider credential-column access for this path. Current v2 Provider encryption reuses the gateway's shared-key software KEK, so true separation requires a distinct provider key domain or the C06 KMS design, migration of existing ciphertext, and management/reveal paths that no longer return plaintext into the gateway process.
- Keep the holder's endpoint private (`workers_dev: false`, no routes or preview URLs), restrict deployment bindings and service target identity, and require the holder to derive Target and credential from committed database facts. The existing [synthetic Images Service Binding](../../../../packages/proxy/scripts/staging/images-gateway.ts) demonstrates a private `Fetcher` call and streamed `Response`; it is not a text holder or production evidence. The current [proxy Wrangler generator](../../../../scripts/deploy/gen-wrangler.mjs) does not emit a text holder binding.
- Cut over [`GatewayBindings`](../../../../packages/proxy/src/app.ts), Worker composition, route planning, Chat dispatch, the failover callback, and OpenAI transport together. Installing v362 alone revokes the current admission LOGIN's v350/v351 mark functions while the live Chat handler still calls them. Keep the old flow gated off for this subset until the holder path and exact rollback/drain procedure are ready; a local gate that accepts a Worker-supplied receipt cannot authorize the old driver's `fetch`.
- The v361/v362 migration transactions lock both reservation tables before changing ACLs, so a global zero-active-hold preflight is technically possible. PG73 rows do not identify which producer created them; normal budget traffic shares those tables, and a global preflight may reject a healthy busy deployment. Database checks also cannot stop an old Worker starting another request immediately after commit. A real cutover must quiesce and drain admission clients across the fleet or first add trusted producer provenance for a selective check.
- Test a real two-Worker Service Binding with distinct bindings and database roles: normal encrypted key success; wrong source generation, candidate, quote body, URL, bearer, and raw upload rejection before provider `fetch`; lost COMMIT/close ACK and nonce replay; crash before and after send; streaming SSE usage, client abort, response-body cancellation, and late headers. Add a route-policy test proving secretless eligibility uses an independently attested subject. Follow with long-stream renewal, unknown/bill reconciliation, buyer settlement, and economic outbox tests before C04 acceptance.

The same-Worker v362 wire test and 20-stage PostgreSQL grant fixture are useful local evidence, but neither exercises this holder boundary. The subsequent [six-field request envelope](../../../../packages/proxy/src/services/chat-text-holder-request-v363.ts) limits data that a future gateway would pass across the binding; no private holder, grant-aware result writer, Service Binding, or deployment was implemented.
