# C04 v368: complete text result resolution and financial closure contract

2026-09-25. **Review only.** This document specifies the missing successor to the local PostgreSQL proposals. It is not executable SQL, an approved unknown-charge policy, an installed migration, a provider bill reconciliation service, or C04 acceptance. No production path should infer a financial result from these proposals alone.

The v366 holder fact writer checks the caller's expected epoch against immutable v365 custody epoch 1. Its provider-bill path requires `mode='active'` custody and copies that same epoch without a caller epoch. The v367 renewal stores later epochs in a **separate** table without changing custody. A successor fact writer must define whether a holder observation is bound to the original send epoch or to the latest acknowledged renewal epoch, and enforce that choice against the renewal ledger. It must also fence stale holder observations at terminal closure. Because v365 custody never becomes terminal, today's v366 bill function may continue appending after a future financial close unless the closer and bill intake replace or extend it together. Late authenticated bills must remain receivable for adjustment; they must not reopen egress or mutate a prior terminal.

The existing lock protocols must be preserved or deliberately replaced as a group. Before acquiring a Guardrail window row, v362 takes `SHARE ROW EXCLUSIVE` on both reservation tables **and** the window table; v365 takes reservation-table `SHARE` before its window row, and v367 renewal takes reservation-table `ROW EXCLUSIVE` before window rows. The v362 table lock conflicts with v365's `SHARE`, so those two paths do not establish a table/window deadlock from row order alone. A successor closer still needs a reviewed common lock order and native races against every active writer, including unrelated requests sharing an account or window.

## Authorities and exact identity

Use direct, mutually isolated `NOINHERIT LOGIN` identities, fixed `SECURITY DEFINER` functions, `SESSION_USER` checks, `READ COMMITTED`, bounded inputs and private tables. The public Gateway may submit the six-field holder envelope and receive sanitized receipts; it must not hold the Provider KEK, append a bill, choose a monetary result, update a grant-linked counter, or execute the closer. The private holder may own exactly one physical fetch and append observations. A separate authenticated provider-bill adapter may append verified provider documents/events but may not grant, renew, send or choose a buyer debit. A renewal actor may only extend all holds for the current run/epoch; a recovery custodian may retain an expired unknown obligation without send authority; a platform resolver/closer may commit one terminal and buyer transaction. Migrator, legacy buyer, delivery consumer and seller/statistics roles remain separate. Function EXECUTE grants alone are insufficient while legacy direct counter DML or `SET ROLE` membership remains available.

Every resolver decision must join stored rows rather than trust caller-supplied copies: `(request_id, quote_id, grant_id, attempt_nonce, attempt_number, candidate_index, route_target_id, provider_id, endpoint_id, credential_class, credential_id, provider_ciphertext_sha256, credential_fingerprint_sha256, final_body_sha256, outbound_body_sha256, outbound_body_canonical_sha256, upstream_url_sha256, send_start_id, holder_run_id, lease_epoch)`. It must bind source-authenticated provider request/event IDs and evidence document digest to that exact frozen tuple, including provider identity and currency. A digest proves byte equality, not who authored the bytes or whether the bill is complete. No raw bearer, ciphertext, URL or upload belongs in the financial event.

## Decision rules before any buyer charge

| Candidate result | Required proof | If proof is missing or contradictory |
| --- | --- | --- |
| `verified_no_fetch` | Under the request lock, permanently fence the holder run after the send-start deadline, see **no** committed v365 marker, and verify no in-flight start transaction can later commit. This relies on the enforced holder rule that physical fetch requires a fresh acknowledged start. A holder `no_fetch_attestation` alone is never sufficient. | Keep `unknown`; a marker that exists without a `fetch_invoked` observation is still possible send. A provider bill without any marker is an incident requiring separate authenticated intake, not evidence to discard. |
| `verified_zero_charge` | A separately authenticated, final provider statement covers the exact send/event and all possible charges for it, with amount zero and a documented provider completeness/finality rule. The zero USD supplier bill and the buyer zero-billable-unit decision are separately checked against the frozen quote. | Holder `provider_zero_charge_observation`, HTTP status, timeout, absent usage or an isolated nonfinal zero event leaves `unknown`. |
| `actual` | Trusted billable units for the exact grant and the frozen v360 buyer tariff yield a deterministic debit; separately authenticated provider bills establish supplier cost. If usage and bills differ, retain both and require a reviewed resolution policy. Verify all grant facts and provider events involved are cited. | A v366 `provider_bill` carries an amount but no buyer token/unit count; a holder `provider_usage` is not an independent supplier bill. Neither row alone computes an authorized buyer debit. |
| `unknown` | A possible send has no complete, trustworthy no-fetch/zero/actual proof. Preserve all holds and the original unknown obligation for recovery. A full-ceiling forfeiture at a bounded hard horizon is **only a separately approved buyer/billing policy**, never a default inference from expiry. | No retry, zero-charge release, silent debit clamp or seller payment. Record an actionable reconciliation state and continue bounded observation. |

The minimal retry successor may unlock attempt 2 or 3 only after a committed `verified_no_fetch` resolution, no send-start or bill contradiction, and fresh source/quote/admission checks under the same request lock. The current v362 function still requires `reserved` holds and returns `pending_unknown`, while v365 permits only one custody row per request; neither permits this retry. A prior actual, zero-charge-but-sent, or unknown attempt is terminal for this minimal retry policy. Supporting cost-bearing fallback later requires aggregation of **every** possibly charged attempt and its own frozen evidence, not just the last successful response.

## One atomic all-hold closer

1. A dedicated platform closer enters with a stable decision nonce and digest. Under the existing request advisory lock it fences new send starts and stale holder reads, verifies no live acknowledged holder epoch can continue, then reads the complete immutable grant/start/fact/renewal set. A chosen fact set is frozen by fact IDs and digests; subsequent authenticated bills are late evidence for a separate adjustment path. Every writer that can change grant-linked authority must observe this request lock or an equivalent database fence. COMMIT and connection-close ACK uncertainty returns no new authority; replay reads the one committed terminal by nonce/digest.
2. Use one reviewed lock order across granter, send-start, renewal, recovery, legacy reapers, legacy buyer and closer: request advisory lock; account row before ordinary reservation; reservation-table `ROW EXCLUSIVE` before any Guardrail window row; exact ordinary and Guardrail reservations; affected windows in deterministic key order. Recheck all v361 intent IDs, counts, amounts, states, server-time deadlines, active counter sums and immutable quote/grant identity **after** blocking locks. A counter mismatch, missing hold or stale epoch aborts the entire transaction. A changed user budget epoch fails closed until an epoch-transfer liability protocol is committed in the reset transaction; never subtract an old hold from a new epoch.
3. Compute buyer debit `B` from the accepted resolution and frozen buyer pricing, separate from provider cost. Require `0 <= B <= R`. For a policy-approved final unknown, `B=R` is a named forfeiture rather than an actual-use claim. Above-ceiling verified evidence is an uncovered liability/incident with a separate debt or adjustment policy, not silently clamped to `R`. The ordinary budget can be unlimited and Guardrail intent count can be zero; those shapes still require a buyer log, terminal and event.
4. Every grant eventually has one immutable attempt resolution. A prior `verified_no_fetch` resolution may have committed earlier to unlock the next grant; the terminal transaction must revalidate and cite it. In **one PostgreSQL transaction**, write the final unresolved attempt resolution and one immutable request terminal citing every grant, resolution, selected fact/digest, frozen quote and chosen debit. For a finite ordinary hold, change exactly one dispatched row to `settled(B)` or approved `expired(R)` and update the same epoch's reserved/spent counters. For each exact Guardrail hold, apply the corresponding terminal state and window `reserved -= R`, `settled += B` (or `R` for unknown). For unlimited ordinary budget, record the buyer debit through its explicitly reviewed no-reservation account/log path. Write exactly one buyer request log and a distinct typed/versioned **platform-grant economic outbox** event covering all grants and certainty, with a stable event ID and no invented seller payout. A protected transaction marker plus deferred verifier must reject a missing/extra row, partial hold close, counter discrepancy, event without log/terminal, log without event, and mismatched debit or snapshot. A caller-set GUC or holder-written receipt is not proof.
5. Same decision nonce/digest returns the already committed terminal with no second debit or event. A conflicting decision, prior legacy log/benefit, or concurrent closer fails and leaves the obligation for review. The v366 hold-freeze trigger, v367 renewal exception, v349 buyer grant policy and old critical-writer route must be replaced **in the same cutover window** as the closer and request-scoped counter writer; a bare `REVOKE` breaks unrelated legacy traffic sharing an account/window, while leaving the old grant runner active reopens direct DML.

After closure, append a later provider bill through an independently authenticated late-bill intake that can correlate the frozen grant even though the old holder run is fenced. Record an exactly-once adjustment ID, prior terminal ID, provider event ID, old/new buyer debit and supplier cost, and the source document. Commit any refund/extra charge, budget-epoch handling and typed adjustment event together; never update the original terminal or outbox event, revive the send slot, or change an old settled hold in place. A late bill above the reserved ceiling or outside the provider correlation policy remains an explicit incident until a separate authority resolves it.
