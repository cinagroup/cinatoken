## 当前实现

新增两个默认关闭的替代候选，使用现有 `cinatoken-staging-recovery-control` 与 `cinatoken-staging-usage-recovery`，不新建资源。控制 Worker 只持有 service binding；接收 Worker 才持有固定 staging `RECOVERY_DB`。命名 RPC 保留 `UsageRecovery`，但此候选的 `run(token)` 与原用量恢复 `run()` 不兼容，不能在其他恢复实验运行时切换。

控制入口固定 origin、路径及空 POST。显式 staging/enable、原生 `ctx.access.aud`、短期 bearer 和固定命令头全部通过后才调用一次 RPC；伪造身份头、查询参数、浏览器 Origin、非空正文及额外参数均不能选择数据库或 SQL。沿用现有一字节 BYOB 空正文验证，原函数只增加导出，没有改动实现。结果仅投影固定有界字段，不回显令牌、SQL、异常或未知 RPC 属性。

接收端在任何 D1 读取前登记生命周期持有；校验固定配置键 `c02_byok_d1_maintenance_v1` 中的许可和令牌摘要，使用完整旧值 CAS 将 ready 改为 pending，然后才检查围栏和生成删除计划。只删除原控制记录与已证明归属的合成行，保留围栏和 maintenance 许可；清理后将许可改为 finished 并保存有界回执。没有 reset/resume、任意排除键、自动解除围栏或重复删除接口。

关闭摘要是**可信操作器的观察凭据**，不是接收端自行查询 Cloudflare，也不证明所有调用路径或在途 SQL 都停止。数据库围栏阻止五张样本表的迟到写入；完整行/schema 守卫仍独立成立。具备配置或 DDL 写权限的操作者不在该保护边界内。

## 主机日志已接通的边界

`scripts/deploy/byok-d1-maintenance-dispatch.mjs` 将现有固定工作区排他日志接到上述控制入口。在发出唯一 HTTP 前记录并刷盘 cleanup/PENDING；最长等待 30 秒，拒绝跳转，成功正文最多 1 KiB，必须核对当前 run、预计删除数量、固定语句数及 retry_safe=false。日志只保存固定计数和回执摘要，不保存凭据。

关键补齐：**数据库认领前发生异常时，许可可能仍为 ready，但主机日志已消费该尝试，仍拒绝重放。** 认领后失败、删除提交后丢 ACK、HTTP 回执丢失、回执刷盘失败或等待取消，也不发第二次 HTTP。超时仅结束主机等待，不证明 D1 已取消；迟到响应仅回收，不把已失败尝试改成成功。失败后独立关闭/撤销步骤仍由既有日志组件允许一次。

这仍是操作器组件，不是完整操作器：冻结构建/费用检查、围栏安装和封闭、可信基线、许可创建、Access 开关、固定用例执行与最终复核尚未串成一条可运行的云端生命周期。调用者不能拿本模块替代这些前置检查。实际项目正式执行占位未创建；测试只使用新建的本地合成工作区。
