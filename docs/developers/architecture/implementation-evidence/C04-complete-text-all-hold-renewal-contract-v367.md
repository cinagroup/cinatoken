# C04 v367 all-hold renewal contract (design gate)

2026-09-25. This records the next required transaction and stream contract. It is **not** an installed renewal, a durable recovery path, or C04 acceptance.

## Current executable boundary

The [v362 grant](../../../../packages/core/migrations-proposals/postgres/complete-text-attempt-grant-v362.sql) stores an immutable `unknown` attempt and moves the exact admitted ordinary and Guardrail reservations to `dispatched` with one `hold_recovery_expires_at` set to server time plus 15 minutes. Its separate `send_expires_at` is at most 30 seconds. [v365 custody/send-start](../../../../packages/core/migrations-proposals/postgres/complete-text-send-start-v365.sql) binds one holder run and one possible send to that initial hold; its start receipt expires no later than the short send deadline. Neither table has a renewal epoch after custody epoch 1. The [v366 reaper fence](../../../../packages/core/migrations-proposals/postgres/complete-text-legacy-reaper-fence-v366.sql) leaves grant-linked rows dispatched but rejects **every** later reservation mutation. The [local holder](../../../../packages/proxy/src/services/private-complete-text-holder-v365.ts) stops an unrenewed stream by a conservative 14-minute active-time abort signal. This protects a local process while it runs; it cannot extend a database hold or recover after suspension or crash.

The same v366 native proof shows the current buyer role can directly update `users.budget_spent`, `users.budget_reserved_micros`, and Guardrail window counters without touching a reservation. The [v349 buyer grant runner](../../../../packages/core/migrations-proposals/postgres/buyer-split-guardrail-runtime-grant-v349.sql) explicitly restores those rights on rerun, while the live PostgreSQL critical writer still uses them for legacy settlement. A reservation-only renewal trigger cannot make the financial counters trustworthy until buyer counter rights, grant policy and the legacy settlement writer are cut over together. The [v366 holder fact writer](../../../../packages/core/migrations-proposals/postgres/complete-text-result-facts-v366.sql) currently accepts only custody epoch 1; a live renewal successor must bind later holder facts to the latest acknowledged epoch or explicitly document why the original send epoch remains the fact identity.

The [v362 granter](../../../../packages/core/migrations-proposals/postgres/complete-text-attempt-grant-v362.sql) takes `SHARE ROW EXCLUSIVE` on the reservation tables **before** locking Guardrail windows; [v365 send-start](../../../../packages/core/migrations-proposals/postgres/complete-text-send-start-v365.sql) also takes reservation-table locks before window rows. The proposed renewer follows that order. A source review alone does not prove fleet deadlock freedom, so cross-request native races remain an acceptance proof, but the earlier suspected v362/v365 window-before-table cycle is ruled out by v362's earlier table lock.

## Required live renewal transaction

1. Give a separate direct `NOINHERIT` renewal LOGIN only `EXECUTE` on a grant-linked renewal function. It has no base-table DML, old mark/forfeit entrypoint, grant insertion, send-start, bill writer, or `SET ROLE` authority. Its holder call contains the immutable `grant_id`, holder run ID, send-start ID, and expected lease epoch; no caller-supplied amount or deadline is authoritative.
2. Serialize by the existing request advisory lock. Verify the v362 grant is still `unknown`, the unique v365 custody and send-start belong to that grant/run, and the expected epoch equals the latest committed epoch. Keep the immutable v362/v365 rows unchanged. An append-only renewal row records epoch, prior deadline, new server-time deadline and the frozen identities. Identical replay after an uncertain COMMIT returns an already-recorded status with **no new egress authority**; a different run or stale epoch fails.
3. Lock the account before reservation tables, obtain the reservation table lock needed for updates **before** any Guardrail window row lock, then lock every exact admitted reservation and affected window. Recheck the v361 intent count and identities, `dispatched` state, markers, amounts, old deadline and nonterminal status; check ordinary and each window's active-reservation sum against its counter. A finite-budget request must have its exact ordinary row; source-proven unlimited requests must have none. Zero Guardrail intents is valid, but the `unknown` grant obligation remains.
4. Use database time after all waits. A live renewal must arrive while the previously committed lease is still valid, and may extend every hold only to a bounded new deadline no more than 15 minutes from that server-time check. Updating one hold without all others, a missing row, counter mismatch, changed epoch or late arrival rolls the whole transaction back. The trigger exception for these exact `expires_at` updates must replace the v366 freeze function in the **same activation transaction**; all other grant-linked reservation DML stays forbidden.
5. Do not extend the quote, admission, original send-start deadline, or consumed attempt. A holder must receive both COMMIT and connection-close acknowledgements before treating the new epoch as live. On an uncertain or rejected renewal it stops upstream reading/sending no later than the previously acknowledged local deadline. A recovery actor may later retain financial capacity for reconciliation, but that path never revives live egress or a fresh send right.

## Required proofs before activation

- Owned PostgreSQL native tests for ordinary-only, Guardrail-only, combined, source-proven unlimited and zero-intent shapes; an exact all-hold extension and append-only epoch should commit, while each missing/changed/terminal row and counter mismatch rolls back every change.
- Direct LOGIN/ACL tests for old buyer counter DML, ordinary and Guardrail legacy settlement continuity, v353/v354 scanners, renewal versus both reapers and send-start, renewal replay, same-request concurrency, lost COMMIT/close ACK, and server-clock expiry after a lock wait. The buyer counter cutover must prove those direct writes are closed without blocking unrelated legacy requests on the same account/window.
- Cross-request races where v362 grant, v365 send-start and renewal share Guardrail windows must show no table/window deadlock under the existing table-before-window order.
- A real streaming holder test crossing the initial 15-minute hold with acknowledged renewals, plus missed heartbeat, worker suspension/cancellation and provider response cancellation. An in-memory timer alone does not prove durable custody. A separate recovery scan must retain an expired but unresolved grant for reconciliation without authorizing another physical send.
- An atomic result closer and economic event protocol must eventually release or settle **all** ordinary and Guardrail holds together. Renewal is custody, not settlement; a holder observation or HTTP status cannot establish zero supplier charge.

Until these checks pass and the writer/trigger cutover is coordinated, v366 remains non-activatable and C04.1–8/G remain unchecked.
