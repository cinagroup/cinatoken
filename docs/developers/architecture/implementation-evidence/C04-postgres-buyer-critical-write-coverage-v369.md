# C04 v369 PostgreSQL buyer critical-write coverage and transaction seam

2026-09-25. **Review only; non-activatable.** This matrix reads the actual [PostgreSQL critical writer](../../../../packages/core/src/db/postgres/critical-writes.impl.ts), its [ordinary settlement type](../../../../packages/core/src/db/user-budget-reservation-types.ts), and its [Guardrail settlement type](../../../../packages/core/src/db/guardrail-budget-types.ts). The new [transaction seam](../../../../packages/core/src/db/postgres/legacy-buyer-held-transaction-v369.ts) accepts the existing Drizzle `tx.execute(SQL)` shape and never opens, commits or closes a connection. The [owned PG18.6 native fixture](../../../../scripts/db/cutover/postgres-complete-text-legacy-buyer-held-v368.native.test.mjs) reports [PASS, cleanup PASS, 32/32 stages](./C04-complete-text-legacy-buyer-held-v368-report.json), including a real buyer LOGIN, request log, audit, v2 economic producer and receipt in one transaction. It is a transaction mechanics proof, not a production writer switch or a verified Provider bill.

## Existing transaction order

All branches below run inside `client.drizzle.transaction(...)` (`critical-writes.impl.ts:409–963`). The ordinary and Guardrail modes are each `actual` or `reserved`; the caller may omit either settlement (`:328–330`, `:362–406`). The function checks request, user, API key, charged cost and economic basis before the transaction (`:335–406`). Its observable lock/write order is:

| Order | Existing action and source |
| --- | --- |
| 1 | Recovery, when supplied, begins first. Otherwise the API key row is locked `FOR UPDATE` and its Workspace checked (`:410–428`). |
| 2 | With an ordinary hold: its row is locked `FOR UPDATE`; existing log and terminal state are inspected (`:432–518`). An active or expired adjustment then locks the user `FOR UPDATE`, writes the user counter when the epoch matches, and writes the reservation (`:525–596`). A matching existing log can return early after economic verification (`:497–515`). |
| 3 | The request log is inserted (`:599–714`). For a shared-key event the log uses conflict-aware replay and calls the v1/v2 economic producer immediately after the insert or replay check (`:692–712`); the database's log trigger takes the request advisory lock only at log insert ([outbox SQL](../../../../packages/core/migrations-proposals/postgres/shared-key-economic-outbox.sql):306–312). |
| 4 | Provider-attempt rows are inserted if present, then daily public-model statistics are upserted (`:715–759`). A charge without an ordinary hold updates `users.budget_spent` here (`:761–769`). The user audit row follows for an ordinary hold or charged budget (`:770–800`). |
| 5 | With Guardrail settlement: active/expired/released reservations are selected `FOR UPDATE` (`:801–818`); active rows are terminalized first (`:838–861`), then each affected window is updated in sorted scope order (`:862–893`). Expired rows with a greater actual amount get a settled-micros and window delta (`:895–935`). |
| 6 | For any positive budget charge, a final set-based window `UPDATE` adds `unreserved_micros` to current user/API-key windows with no matching active or terminal reservation for this request (`:939–960`). Recovery finalization, if present, is last (`:962`). |

This is **reservation before account** for an ordinary held path, while the [v368 function](../../../../packages/core/migrations-proposals/postgres/complete-text-legacy-buyer-held-writer-v368.sql) takes request advisory, API-key share, account, reservation-table, reservation-row and window locks in that order. A real integration must move the request lock ahead of the current API-key/ordinary prelude and replace the direct ordinary/Guardrail writes. Merely calling the helper after the present reservation lock can invert the lock order against v362/v365 and the proposed renewal/closer.

## Buyer settlement coverage matrix

“Current writes” lists the financial writes in addition to the common log, optional provider-attempt rows and statistics. The v368 function supports only the first row's narrow SQL transition; v369 proves only that this transition can share a Drizzle transaction with the buyer log, audit and real v2 event.

| --- | --- | --- |
| Active ordinary hold, `actual`, current epoch | `users.budget_reserved_micros -= reserved`; `budget_spent += actual`; ordinary state `settled`, settled micros actual (`:463–465`, `:561–596`). | SQL transition supported only when all Guardrail rows are charged-basis, active, and amounts fit each hold. Caller amounts remain unverified. |
| Active ordinary hold, `reserved` ceiling | User reserved decreases, spent increases by the **reserved ceiling**; ordinary state becomes `expired` (`:463–465`, `:561–596`). ## Same-transaction native result and remaining interface

The v369 helper is called from a Drizzle buyer transaction and returns `staged_legacy_settlement`, never `commitAcknowledged`. The native fixture first rolls back the helper's user/hold/window changes **together with** a real request log, audit row and v2 event. It then commits the same sequence and observes one ordinary terminal hold, three Guardrail terminal holds, one log, one audit, one v2 event and one event attempt. The economic producer marker and buyer budget receipt have the same PostgreSQL transaction ID as the outer transaction; the event debit and account spent delta are both one micro. The direct buyer still has no raw counter or hold `UPDATE` rights under the fixture's v368 policy.

This proves a suitable **transaction object shape**. To wire production, the existing critical writer must accept a reviewed request-bound amount source and call the request-scoped operation at the correct lock point while replacing all its direct user, ordinary-hold, Guardrail-hold, window and late-adjustment writes. It must keep its full log, audit, statistics, provider-attempt and v1/v2 economic-event behavior and replay semantics within that outer transaction. The v368 SQL still accepts caller-supplied amounts bounded by holds rather than an authenticated Provider bill or immutable buyer fact. The [separate-connection v368 client](../../../../packages/proxy/src/services/postgres-legacy-buyer-held-v368.ts) remains a review artifact and cannot be composed with this transaction. No existing application writer was edited here, no formal migration was added, and neither v368 nor v369 is authorized for activation.
