## Official OpenAI API boundary, checked 2026-09-25

These claims apply only to a route verified to be an OpenAI-owned API account and endpoint. An OpenAI-compatible third-party host needs its own provider-specific source contract.

- The [organization Costs API](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage/methods/costs) returns **day buckets** and can filter or group by project, line item and API key. Its documented result is an aggregated amount, not an item keyed by Chat request ID. It is useful for reconciliation, but the documented response cannot populate an authenticated per-grant `providerEventId` and `amountMicros` by itself. This last sentence is an inference from the documented query and result schema.
- The [organization Completions Usage API](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage/methods/completions) returns **minute/hour/day buckets** with aggregates and grouping by project, user, API key, model, batch or service tier. It has no documented grant/request-ID selector or itemized charge in that schema. A one-request bucket is still an aggregate observation without a documented bill finality rule. This is an inference from the documented schema.
- OpenAI documents an `x-request-id` response header and an optional caller-supplied `X-Client-Request-Id` for [support/debug correlation](https://developers.openai.com/api/reference/overview#debugging-requests). OpenAI says the latter is logged for Chat Completions and can help support find a request after a timeout. The docs do not say this header is a billing event, idempotency key, public lookup API or final zero-charge certificate. The holder currently supplies neither a client request ID nor a durable captured server ID.
- The [Chat streaming usage option](https://developers.openai.com/api/reference/resources/chat) can return a final usage chunk, but the docs warn it may be absent if the stream is interrupted. Usage is token accounting observed through the holder, not an itemized invoice. The [stored Chat completion retrieval endpoint](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/retrieve) requires a completion created with `store=true`; v360's allowed request body has no `store` field. Even a retrieved completion would prove response/usage under that API, not its final supplier charge.

**Current OpenAI public API conclusion:** the reviewed Costs, Usage, request-ID, streaming and stored-completion interfaces do not supply the independently authenticated, final **per-request cost event** that v366's `provider_bill` name suggests. This does not establish that no commercial statement or provider-specific integration could supply one. Keep any OpenAI bucket data in a reconciliation lane; do not convert it into per-request bill facts by dividing, tariff multiplication, or assuming no other request shared a bucket.

## Minimum authority and correlation contract

A provider-specific intake may submit a cost candidate for review only after all of these checks are implemented and recorded:

1. **Source registry.** Pin the provider's official billing source, account/project, credential scope and accepted event/document format to the internal `provider_id` and the frozen route. Bind the true upstream origin and provider account to the grant. `upstream_url_sha256`, a display name, `provider_id`, encrypted credential hash and OpenAI protocol compatibility alone are insufficient. Reject unknown hosts, resellers without their own authoritative ledger, and a statement from a different account.
2. **Independent acquisition.** The bill adapter retrieves the event over its own authenticated provider channel or verifies the provider's signed delivery, with replay protection and source rotation handling. The holder/public Gateway must not possess the adapter's provider billing credential or database bill LOGIN. Retain exact source bytes securely and record a digest, retrieval time, authenticated account, method, verifier version and immutable source event ID. A holder-forwarded JSON body, response header or callback parameter is only a lead for lookup.
3. **Exact event binding.** Join a provider-assigned request/event reference found in the independently obtained item to a durable holder send record for the *same* `(request_id, quote_id, grant_id, attempt_nonce, candidate_index, route_target_id, provider_id, endpoint_id, credential_id, outbound_body_sha256, upstream_url_sha256, send_start_id, holder_run_id)`. A provider-reported model, account, charge class and currency must match the registered route. A stable holder-generated correlation ID may assist lookup, but it must be unique per physical attempt and independently echoed or resolved by the provider. An equal string supplied solely by the holder is not correlation proof.
4. **Amount and completeness.** Require a provider-authored itemized charge or adjustment with exact currency and integer amount conversion, documented timing/finality and a rule covering all charges for that attempt. Preserve multiple legitimate provider events and adjustments rather than assuming one event. A zero amount authorizes `verified_zero_charge` only if the provider's source contract proves that the event is final and covers every possible charge for the exact send. An absent event, 4xx/5xx, timeout, aborted stream, missing usage chunk, or a zero aggregate bucket does not prove zero.
5. **Separate financial decision.** Feed authenticated supplier-cost events to a resolver, not directly to the buyer critical writer. Derive buyer units and debit from separately accepted usage evidence plus the frozen v360 buyer tariff. Compare with the full reserved ceiling and hold set; over-ceiling and conflicting evidence need an incident or approved adjustment path. The resolver must freeze cited fact IDs/digests, preserve unknown send liability, and produce one atomic buyer terminal/log/platform event as specified in v368.

The existing v366 JSON schema has no fields for source account, acquisition method, verification result, finality/coverage or an authenticated link from event to holder request reference. Its `provider_bill` row can remain an **unverified candidate** in review data, but a successor schema/adapter and resolver must make those facts explicit before treating it as financial authority. Late bills after a terminal need their own authenticated intake and exactly-once adjustment, because v366 currently requires active custody and a send-start marker.

## Denial matrix for the current implementation

| Proposed source for a v366 bill | Decision now | Reason |
| --- | --- | --- |
| Holder response `usage`, response `x-request-id`, error body, or holder-supplied `cost` | Observation only | Same actor controls the observation and physical send; no independent provider ledger or final amount. |
| `provider_zero_charge_observation` or no response | Remain unknown | Neither covers later provider charges. |
| OpenAI organization Costs/Usage bucket | Reconciliation only | Aggregate with no documented per-request cost/event key or final zero rule. |
| Matching `providerRequestRef`, self-computed document hash and valid bill LOGIN | Unverified candidate | Syntactic equality and local caller authentication cannot establish supplier authorship or account ownership. |
| Independently retrieved provider item with a different grant, account, request ref, currency or nonfinal status | Reject and preserve conflict | Source may be real but cannot authorize this attempt's charge. |
| Independently authenticated, itemized and final provider event with exact binding | Eligible for future source verifier | Requires a named provider-specific adapter, source registry and persisted verification record; none exists in this worktree. Eligibility still does not choose buyer debit. |

## Next integration with falsifiable gates

1. Choose the actual upstream provider class for the initial production route. For each provider, obtain a primary source specification or contract for itemized request charges, identity binding, finality, late adjustments and zero-charge coverage. If no such source exists, keep supplier cost unknown and choose an explicit approved unknown-liability policy; do not fabricate per-request bills from OpenAI-compatible response fields.
2. Add a durable per-attempt correlation ID to the holder's prepared outbound header only where the provider documents support for it, and persist the server request ID as an observation when available. If adding a header, bind it into the grant's exact prepared request and test one physical POST, redirect refusal, lost response and no accidental retry. Do not treat this correlation improvement as provider authentication.
3. Provision an independent adapter with provider billing credentials, allowlisted source origins and its own bill database LOGIN. Introduce a read-only grant identity projection and a successor verified-source table or typed bill function that cannot be called by holder/public roles and cannot accept caller-invented verification flags. Capture evidence bytes/digest, account, source event, request mapping, finality, verifier version, adjustment lineage and status under one idempotent key.
4. Test same-reference wrong provider/account/grant, forged document digest, replayed provider event, simultaneous duplicate intake, missing start, late bill, nonfinal zero, multi-event charge and above-ceiling evidence against direct separate LOGINs. A synthetic webhook signature test only proves the parser and signature implementation; staging provider data is needed for external authenticity and completeness. Keep C04.2/result closure open until that proof and the atomic closer exist.

No review-only validator can truthfully return `authoritative` for the current generic v366 payload: the provider source format, independent credential and per-request financial evidence are absent. For that reason this audit adds no self-asserted `verified=true` code path or mock positive result.
