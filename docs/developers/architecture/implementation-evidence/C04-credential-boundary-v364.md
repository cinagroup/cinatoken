# C04 Provider credential and route authority boundary (v364 audit)

2026-09-25. Review-only audit of the current Worker/PostgreSQL path for the v360 **platform credential, OpenAI Chat, flat text** subset. No key migration, role change, holder activation, live send, or C04 acceptance is implemented here.

## Observed authority path

1. `resolveWorkerStorageFromBindings` opens the ordinary Worker database from `HYPERDRIVE`, requires `SHARED_KEY_ENCRYPTION_SECRET`, and decorates the Provider repository with the same secret used for shared and BYOK keys ([`workers.ts:17-40`](../../../../packages/proxy/src/runtime/workers.ts#L17-L40), [`runtime-database-config.ts:74-110`](../../../../packages/core/src/storage/runtime-database-config.ts#L74-L110)). The Node path makes the same Provider decoration ([`node.ts:32-50`](../../../../packages/proxy/src/runtime/node.ts#L32-L50)). The environment Provider wrapper also substitutes `DEEPSEEK_API_KEY` into runtime reads ([`workers.ts:29-35`](../../../../packages/proxy/src/runtime/workers.ts#L29-L35), [`provider-key-environment.ts:78-126`](../../../../packages/core/src/lib/provider-key-environment.ts#L78-L126)); v360 excludes those `env:` references because it requires stored `enc:v2:` ciphertext.
2. The Provider encryption wrapper decrypts `enc:v2:` on `getProvidersByIds`, returns the plaintext row, and may write an online upgrade for legacy rows ([`provider-key-encryption.ts:77-113`](../../../../packages/core/src/lib/provider-key-encryption.ts#L77-L113), [`provider-key-encryption.ts:167-193`](../../../../packages/core/src/lib/provider-key-encryption.ts#L167-L193)). PostgreSQL `getProvidersByIds` currently uses `SELECT *` from `providers` ([`providers.impl.ts:82-95`](../../../../packages/core/src/db/postgres/providers.impl.ts#L82-L95)). The route resolver calls that method, verifies the endpoint subject, and copies both raw endpoints and the plaintext key into `RouteResult` ([`model-router.ts:87-93`](../../../../packages/proxy/src/services/model-router.ts#L87-L93), [`model-router.ts:171-197`](../../../../packages/proxy/src/services/model-router.ts#L171-L197), [`model-router.ts:321-361`](../../../../packages/proxy/src/services/model-router.ts#L321-L361)). It also records a key-tail fingerprint in that route object.
3. Chat dispatch passes this `RouteResult` through `proxyChatCompletions` into `dispatchOpenAiRoute` ([`chat.ts:642-670`](../../../../packages/proxy/src/routes/v1/chat.ts#L642-L670), [`proxy.ts:194-227`](../../../../packages/proxy/src/services/proxy.ts#L194-L227)). The driver resolves the upstream URL, transforms the body, resolves the effective key or OAuth token, builds `Authorization: Bearer`, calls the optional admission callback, and then performs `fetch` ([`openai-driver.ts:807-881`](../../../../packages/proxy/src/services/egress/openai-driver.ts#L807-L881)). Thus the current gateway already has every capability needed to send. The v361 local gate requires `route.providerApiKey.startsWith('enc:v2:')`, so a normally decrypted live route fails that check and its ciphertext digest cannot be derived from this route object ([`chat-text-grant-egress-contract-v361.ts:69-113`](../../../../packages/proxy/src/services/chat-text-grant-egress-contract-v361.ts#L69-L113)).
4. Route planning is also credential dependent. `computeRouteDataPolicySubjectFingerprintFromRows` hashes the *plaintext* credential and the protocol endpoint into the canonical subject ([`route-data-policy.ts:50-106`](../../../../packages/core/src/route-data-policy.ts#L50-L106)); the resolver requires that computed subject to match the verified endpoint binding ([`model-router.ts:342-360`](../../../../packages/proxy/src/services/model-router.ts#L342-L360)). Removing only the key from the route row makes existing verification fail. Endpoint backfill computes this subject from Provider rows as well ([`model-endpoint-backfill.ts:1623-1655`](../../../../packages/core/src/model-endpoint-backfill.ts#L1623-L1655)). The v359 source attestation records a generation and subject fingerprint, invalidates on Provider/route/endpoint changes, and gives a separately named verifier LOGIN its write entry point; the function requires the verifier to compute the subject independently before calling it ([`authenticated-text-route-source-fence-v359.sql:125-153`](../../../../packages/core/migrations-proposals/postgres/authenticated-text-route-source-fence-v359.sql#L125-L153), [`authenticated-text-route-source-fence-v359.sql:230-288`](../../../../packages/core/migrations-proposals/postgres/authenticated-text-route-source-fence-v359.sql#L230-L288)). A gateway-supplied fingerprint alone would not be an attestation.
5. The default PostgreSQL runtime grant gives `cinatoken_gateway_runtime` table-wide `SELECT, INSERT, UPDATE, DELETE` on existing gateway tables, including `providers`, before its specific revokes ([`grant-postgres-runtime.ts:73-103`](../../../../scripts/db/cutover/grant-postgres-runtime.ts#L73-L103)). A `REVOKE SELECT(api_key)` cannot override table-wide `SELECT`; the table grant must first be removed and replaced with explicit non-secret column rights, and queries must stop using `SELECT *`. The current Proxy and Admin Wrangler generation both call `applyWorkerDatabaseRuntime` with the same `HYPERDRIVE_ID` ([`gen-wrangler.mjs:196-212`](../../../../scripts/deploy/gen-wrangler.mjs#L196-L212), [`gen-wrangler.mjs:291-358`](../../../../scripts/deploy/gen-wrangler.mjs#L291-L358)). The Admin Worker has its own Provider decryption/reveal path but currently uses the same software secret and can reveal plaintext ([`storage-context.ts:33-54`](../../../../packages/admin/lib/storage-context.ts#L33-L54), [`providers-service.ts:173-182`](../../../../packages/admin/lib/services/admin/providers-service.ts#L173-L182)). Proxy and Admin therefore need separate database identities before a Proxy-only Provider column revoke.
6. `providers.endpoints` is also potentially secret-bearing. The write validator checks URL scheme but does not ban userinfo or query strings ([`provider-endpoints.ts:279-300`](../../../../packages/core/src/provider-endpoints.ts#L279-L300)); the prepared wire identity explicitly recognizes query-key and URL-userinfo auth surfaces ([`prepared-text-attempt.ts:84-117`](../../../../packages/proxy/src/services/egress/prepared-text-attempt.ts#L84-L117)). A secretless gateway route view cannot include the raw endpoint map or a derived URL merely because it omits `api_key`.

## Smallest safe migration sequence for the strict subset

1. **Create distinct principals and projections before changing dispatch.** Give Proxy ingress, Admin management, the v359 verifier, Provider credential custody, and v362 grant issuance separate direct database LOGINs and separate Worker bindings. The v362 granter is intentionally `NOINHERIT`, can execute only its grant function, and has no grant-table DML ([`complete-text-attempt-grant-v362.sql:723-775`](../../../../packages/core/migrations-proposals/postgres/complete-text-attempt-grant-v362.sql#L723-L775)); the holder needs a separate, narrow credential/source reader. Introduce a Proxy Provider projection with only routing metadata and a distinct `PlannedRoute` type containing IDs, verified endpoint capability, pricing, and an attested generation/subject token. It must have no `providerApiKey`, raw `providerEndpoints`, upstream URL, ciphertext, key-tail fingerprint, or callable `fetch` driver shape. The holder loads the complete route privately from committed facts.
2. **Preserve policy semantics through trusted verification.** Move the plaintext-dependent route-subject computation and v359 verifier invocation to an independent credential-aware process. Make ingress consume only a fresh database-backed equality of link subject, verified subject, and source generation, with endpoint expiry checked. The v360 quote and v362 grant already require this source state and compare the live ciphertext hash to the quote manifest ([`authenticated-complete-text-quote-v360.sql:317-367`](../../../../packages/core/migrations-proposals/postgres/authenticated-complete-text-quote-v360.sql#L317-L367), [`authenticated-complete-text-quote-v360.sql:419-445`](../../../../packages/core/migrations-proposals/postgres/authenticated-complete-text-quote-v360.sql#L419-L445), [`complete-text-attempt-grant-v362.sql:356-385`](../../../../packages/core/migrations-proposals/postgres/complete-text-attempt-grant-v362.sql#L356-L385)). Keep the authoritative route and policy recheck inside the holder/granter; the ingress token supports planning only. Reject stale or absent attestation instead of recomputing with a blank credential.
3. **Move Provider unwrap authority, then revoke ingress reads.** Current `enc:v2:` Provider keys use the shared-key software KEK and Provider-specific HKDF context ([`provider-key-encryption.ts:1-12`](../../../../packages/core/src/lib/provider-key-encryption.ts#L1-L12)). A holder that receives the same KEK while Proxy retains it is a transport split, not credential isolation. Add a distinct Provider key domain or KMS unwrap policy; rotate or rewrap eligible ciphertext; move Provider create/patch/reveal to a separately authorized management path; and update the versioned v360/v362 ciphertext-prefix contract together. Keep the legacy key format only behind a drained old path. Revoke table-wide `providers` SELECT from the Proxy LOGIN, grant explicit non-secret columns, prove `SELECT api_key`, `SELECT endpoints`, `SELECT *`, role inheritance/`SET ROLE`, and direct grant execution all fail under that exact LOGIN. If other platform routes still require the old Proxy Provider repository, isolate this strict ingress in a different Worker and database role until those routes migrate; one Worker with the old KEK and read privilege cannot claim an independent Provider holder for C04.
4. **Cut over the physical sender as one unit.** After the above, the gateway may send only the six-field v363 envelope over a private Service Binding ([`chat-text-holder-request-v363.ts:10-18`](../../../../packages/proxy/src/services/chat-text-holder-request-v363.ts#L10-L18)). The holder independently loads the v360 manifest, body digest, route source, endpoint and credential, rejects URL userinfo/query/fragment for this strict class unless separately specified, constructs and hashes its own frozen upload and bearer, obtains the v362 grant through its dedicated LOGIN, waits for transaction commit and connection-close acknowledgements, and makes one `POST` with redirects disabled. Keep response parsing and usage collection on the gateway side without returning URL, key, or holder database authority. v362's `SESSION_USER` check and direct-execute ACL form only the database half of this boundary ([`complete-text-attempt-grant-v362.sql:187-202`](../../../../packages/core/migrations-proposals/postgres/complete-text-attempt-grant-v362.sql#L187-L202)). The v363 result/lease audit lists the independent outcome and all-hold recovery work still required before live C04 acceptance.

## Cutover evidence required

- Native PostgreSQL privilege test with the generated Proxy, Admin, holder reader, verifier, and granter connection strings, plus `pg_has_role`/effective column privilege checks. Include a rerun of the runtime grant reconciler so broad defaults cannot silently restore Provider reads.
- Real Worker route test where encrypted Provider ciphertext is callable only by holder; ingress planning still accepts a fresh attested subject and rejects a changed Provider key or endpoint after v359 invalidation. Assert no key, endpoint URL, query secret, ciphertext, or key-tail fingerprint appears in the binding request, gateway route DTO, or error/log projection.
- One physical-attempt fixture for an exact v360 quote and six-field envelope: wrong body/candidate/route/credential/source, lost commit or close ACK, replay, redirect, cancellation, and a changed frozen upload must produce zero extra `fetch` calls. The local v362 wire proof and isolated grant SQL fixture do not establish this cross-Worker property.
