# C04 snapshot earning consumer, review only (v340)

The [proposal SQL](../../../../packages/core/migrations-proposals/postgres/shared-key-snapshot-earning-consumer.sql) adds a private PostgreSQL consumer boundary after formal PG73, the v338 immutable quote proposal, and both v339 dispatch-attempt and economic-outbox proposals. It does not install a formal migration or activate a production worker, queue, payout, or runtime grant. The only delegated operation is `consume_shared_key_economic_event(event_id)` for a dedicated LOGIN; ordinary runtime and direct table access are denied.

The consumer locks the committed event, reads every immutable attempt outcome with its own claimed quote version, and writes one append-only decision per attempt. It uses quote-version seller prices, seller ID, commission, currency and unit. It does not read current Key price, current commission configuration, current owner, or `provider_cost_micros` as seller gross. PostgreSQL `NUMERIC` computes gross micros as `ROUND(sum(tokens × quote USD per million))`; fee micros is `CEIL(gross micros × quote commission)`; net micros is the difference. This matches the existing nonnegative six-decimal gross and upward commission policy without JavaScript floating-point arithmetic.

A positive seller balance credit requires both an actual buyer charge basis and an attempt with confirmed `actual` or `confirmed_zero` usage **and** provider-cost certainty. An asserted `actual` fact also needs a provider usage or bill evidence label; timeout, cancellation and manual labels are not automatic payout evidence. `unknown`/`estimated` attempts, and events without actual buyer basis, become durable `pending_manual` decisions with no balance or ledger credit. A v1 pending decision is not rewritten if late facts arrive; C05 still needs a separate adjustment-event contract. An event with a mix of confirmed and unresolved attempts credits only its confirmed attempts. A confirmed-zero attempt leaves a zero-value consumption and ledger row.

For each confirmed attempt, the detail insert, `user_earnings` micro and displayed counters, and `portal_ledger_entries` row run in the same transaction as the event consumption marker. The event row lock and event/attempt keys serialize replay, including an unknown commit ACK. A credit takes its timestamp only after acquiring the seller account row lock; it advances to at least one microsecond after that account's prior `updated_at`, and the ledger takes `created_at` from the returned account row. This keeps ledger time in balance order even when an earlier-started event waits on a different log lock. Existing v339 outbox guards reject legacy `shared_key_earnings` insertion for the same request log, and the consumer checks that legacy row again under the log lock. This prevents the old synchronous path from paying the same enrolled event during cutover; it does not migrate historical legacy earnings.

The [native fixture](../../../../scripts/db/cutover/postgres-shared-key-snapshot-earning-consumer.native.test.mjs) ran on an owned loopback PostgreSQL **18.6** cluster. The pinned [machine result](./C04-postgres-snapshot-earning-consumer-v340-results.json) and [full report](./C04-postgres-snapshot-earning-consumer-v340-report.json) show **23/23 stages PASS, cleanup PASS**. Tested boundaries include exact PG73 ledger and default-off activation; missing/disabled legacy guards; hostile default and delegated grant options; direct-role denials; rollback before commit; repeated and concurrent deliveries; a two-event same-seller race with opposite call-entry and credit order, asserting strictly increasing ledger timestamps with balances; mixed known/unknown, estimated, reserved, and timeout-labeled forged actual facts; confirmed zero; two distinct quote/commission versions within one event; half-micro gross rounding and ceiling commission; reprice plus revocation after claim; ledger uniqueness failure with complete rollback and replay; and legacy double-pay rejection. The first positive credit also verified `user_earnings(user_id)` insertion against the exact PG73 defaults and all three micro counters.

Run the owned native fixture with `GATEWAY_NATIVE_PG_BIN` set to the local PostgreSQL 18.6 `bin` directory:

```powershell
node --test scripts/db/cutover/postgres-shared-key-snapshot-earning-consumer.native.test.mjs
```

Limits: The buyer critical writer now has a default-off, explicit `economicOutbox` option, but no `recordUsage` caller supplies it, and no consumer worker or operational retry/lease is wired. Buyer `actual` certainty remains an asserted input from a future trusted caller, not something the fixture infers from the legacy log. The proposal uses the current withdrawable seller balance for confirmed facts; C12's pending/available/hold and financial release policy remains open. Existing `shared_keys` usage totals and Admin projections are not updated here and need the C04.7 rebuildable-statistics path. A backward database clock can make the one-microsecond monotonic account timestamp briefly newer than wall time; the legacy synchronous earning trigger for other logs still has its separate timestamp policy. D1/MySQL, production critical-write behavior, late adjustments, owner-transfer settlement, and end-to-end production crash recovery are unverified. The fixture is registered in the local CI workflow, but Linux CI has not run. C04.4, C04.5 and C04.G remain open.
