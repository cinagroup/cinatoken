# C04.7 credited-usage reader authorization boundary (v346, review only)

The [v344 private reader](../../../../packages/core/migrations-proposals/postgres/shared-key-credited-usage-reader.sql) deliberately accepts a seller ID only from the direct migrator LOGIN. It revokes schema `USAGE` and function `EXECUTE` from `cinatoken_gateway_runtime`. The [seller route](../../../../packages/admin/lib/routes/user/shared-keys.ts) obtains `principal.userId` after portal authentication and the [adapter](../../../../packages/admin/lib/shared-key-credited-usage-reader.ts) checks returned owner IDs. These are useful response checks, but on the PostgreSQL path the Admin and portal services resolve the [same configured storage binding](../../../../packages/admin/lib/storage-context.ts), without an individual SQL LOGIN for each HTTP principal. PostgreSQL sees the binding's LOGIN, not the user. Removing the migrator-only check and granting runtime `EXECUTE` would let any SQL caller supply another seller ID; merely adding `EXECUTE` to the present function would still fail closed at that check.

The [native PG18.6 negative fixture](../../../../scripts/db/cutover/postgres-shared-key-stats-auth-boundary-v346.native.test.mjs) installed exact formal PG73 and ran the real `grant-postgres-runtime.ts`. All **5/5 stages passed; cleanup PASS**. With an actual `cinatoken_gateway_runtime` password session, it proved that the broad grant permits `SELECT`, `INSERT`, and `UPDATE` on `portal_sessions` and `INSERT` on `users`. The migrator seeded an existing `cinaauth` seller; runtime then minted its own valid, hashed bearer session for that seller and resolved the victim's ID through the same subject mapping used by portal authentication. It also set and read an arbitrary seller GUC. Therefore deriving the DB reader's seller from a bearer token stored only in these mutable tables, or from a session GUC, would still let the ordinary SQL role forge a seller. A dedicated read LOGIN alone separates table privileges but does not attest the seller of each HTTP request. The v344 reader's separate native fixture already proves the ordinary runtime gets `42501`, including after the real broad grant reruns; this v346 fixture does not install the private reader.

## Required cutover contract

1. A separately trusted identity authority must issue a short-lived, audience-bound `stats.read` claim for the authenticated seller, or a separate reviewed admin claim for all-seller reads. The claim must bind subject, seller ID, expiry, request or nonce, and any permitted key scope. Ordinary gateway SQL must be unable to mint or alter a valid claim, its signing key, its issuer records, or its revocation state. Moving a signing secret into the current shared runtime process would not establish this boundary against compromise of that process.
2. A dedicated direct PostgreSQL reader LOGIN must have only the reviewed schema `USAGE` and function `EXECUTE`, with no table reads or writes, no migrator/runtime membership, and no role switch. The `SECURITY DEFINER` function must verify the issuer's signature, audience, expiry, revocation/freshness, caller LOGIN, and key owner in PostgreSQL before projecting the v344 audited summary. The verification material must not be readable or replaceable by ordinary runtime. Signature algorithm and PostgreSQL verification facility need an explicit, tested choice.
3. The Admin all-seller path needs its own authorization claim tied to current `providers.read` permission. Seller and Admin endpoints must use the correct dedicated connection and fail closed when the claim, reader readiness, role, or owner check fails. Connection pool reuse and Hyperdrive transaction pooling must not carry one request's identity into another; no caller-controlled GUC may act as an authority.
4. Formal migration, both historical backfills, full-history audit, production-sized lock/latency measurement, exact grants, grant-script rerun checks, and role/credential deployment evidence are required before `SHARED_KEY_CREDITED_USAGE_READER` is enabled.

**Decision:** keep runtime `EXECUTE` and the application flag disabled. C04.7 remains open. This evidence rules out the two tempting authorization shortcuts, but does not supply the independent issuer, DB signature verification, direct reader binding, or production activation.

Sources: [PostgreSQL 18 function security](https://www.postgresql.org/docs/18/sql-createfunction.html) explains the `SECURITY DEFINER` privilege and search path requirements; the [PostgreSQL 18 SHA-256 function](https://www.postgresql.org/docs/18/functions-binarystring.html) computes a digest but does not authenticate a claim issuer.
