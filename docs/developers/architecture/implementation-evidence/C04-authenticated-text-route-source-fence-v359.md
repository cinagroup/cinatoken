# C04 one-target route source freshness fence (v359)

2026-09-25. **Review-only local PostgreSQL proposal.** The [v359 SQL](../../../../packages/core/migrations-proposals/postgres/authenticated-text-route-source-fence-v359.sql) overlays the [v357 one-target text ceiling](./C04-authenticated-text-route-ceiling-v357.md). Its purpose is narrow: a persisted route-link subject fingerprint alone cannot establish that the route, provider, pool, Endpoint, and link still match the data verified earlier. This proposal does not create a complete quote, budget reservation, or physical dispatch grant.

## Contract proved locally

The installer requires formal PG73, v356/v357, a clean direct `NOINHERIT` verifier LOGIN, and an explicit transaction-local activation flag. It seeds every existing route at generation 1 **without** verification. A trusted verifier reads the generation **first**, then current route/provider/pool/Endpoint/link rows, derives the JS route subject from the provider configuration, and calls the restricted attestation function with that first generation and fingerprint. The function locks those rows, compares the persisted link fingerprint and generation, and stores a hash of the locked source rows. The runtime cannot write the generation table or call the attestation function. The verifier can read source rows and the generation table but cannot write them.

Row triggers advance the generation and clear verification on every insert, update, or delete of a route, provider, pool, Endpoint, or link. An update that restores the original value still advances the generation. Source-table `TRUNCATE` is rejected because it would bypass row triggers and could allow an old route ID to return. A new `BEFORE INSERT` trigger on v357 fragments requires an attested, current generation and the same link fingerprint, then stamps the generation and attested source hash. Existing fragments have NULL in these new columns and cannot be treated as fresh by a future grant.

The isolated [PG18.6 fixture](../../../../scripts/db/cutover/postgres-authenticated-text-route-source-fence-v359.native.test.mjs) ran **1/1 test, 15/15 recorded stages, cleanup PASS**. It installed the 73 formal migrations, current runtime grants, v356, v357 and v359 in a disposable cluster. It proved an apparently valid preexisting link cannot quote before attestation; direct runtime/issuer writes and calls are denied; provider change and ABA restoration invalidate; Endpoint repricing invalidates and changes the next database-derived amount; no-op route/pool updates invalidate; link fingerprint substitution invalidates; an old immutable fragment remains stale. Deleting and reinserting the same route ID also advances its retained generation and requires reattestation. A verifier blocked behind an uncommitted provider mutation rejects its old generation after that writer commits. It checked activation, verifier DML contamination, runtime and quote issuer membership in the migrator role, direct and parent-cascade `TRUNCATE` rejection, and the legacy broad-grant rerun block. The [machine report](./C04-authenticated-text-route-source-fence-v359-report.json) records source hashes and all stage names. The fixture is registered in the local CI workflow; Linux CI has not run here.

## Remaining boundary

The verifier LOGIN is a proposed trust boundary, not a deployed service. The fixture computes the subject from synthetic provider rows; real encrypted credentials need an independently controlled verifier with the application decryption key. The SQL cannot prove the verifier supplied a correctly computed JS fingerprint; it can enforce the supplied fingerprint against the locked persisted link and a monotonic generation. A future request issuer must atomically quote **all** eligible route and credential attempts before claiming the v356 capability, and its budget/egress grant must recheck the saved generation and current Key/source facts under locks. The [complete quote audit](./C04-complete-request-quote-boundary-v358.md) shows why v357 cannot be repeated to build that plan. No current grant consumes v359, and no physical text fetch compares its prepared URL, body, or credential with a committed grant.

This remains outside formal migrations and is default off. PG73/D1 68/MySQL 64 are unchanged; no remote SQL, deployment, or cloud request was made. C04.1–8/G remain open.
