# C04.6 dedicated scanner backlog observation bridge (v354)

Status: **local review only, default off**. No Worker was deployed, no activated Wrangler config was written, and no remote SQL or Cloudflare API was called.

The [dedicated scanner](../../../../packages/proxy/src/runtime/postgres-shared-earning-scanner.ts) now calls the [narrow backlog observer](../../../../packages/proxy/src/runtime/postgres-shared-earning-backlog-observer.ts) through its delivery LOGIN **before** the first `claim_events` call. The observer opens a read-only transaction, verifies the direct delivery `CURRENT_USER`/`SESSION_USER` and database-user statement, transaction, lock and idle deadlines, then calls the [v353 function-only proposal](../../../../packages/core/migrations-proposals/postgres/shared-key-delivery-backlog-observation.sql) with a fixed cap of 1000. It accepts one complete, typed response after a confirmed transaction result. A missing function, wrong LOGIN, malformed response or lost COMMIT acknowledgement rejects the scheduled operation before a consumer connection opens. No automatic retry or alternative raw jobs-table query is used.

The scheduled path emits one structured `gateway.shared_earning_scan.backlog` record containing only observation time, cap, capped counts, saturation flags and the pending due-time age. It emits no event ID, claim token, amount, buyer or seller identity. The existing lease → consumer marker → ACK sequence is unchanged after a successful observation. Disabled invocation still opens no database connection; the separate Worker has no HTTP financial action or general proxy binding. The v352 `dedicated-v1` activation now requires the v353 function to be installed before any scan can proceed.

## Remaining gate

The observation is a capped lower bound when saturated. Its age is based on the earliest pending `next_attempt_at`, not original event residence time. No deployed Worker log, representative physical query plan, production arrival rate, backlog SLO, alert threshold, dead-letter recovery capacity or Hyperdrive pool budget was measured. The hourly Cron still claims at most 20 events per invocation. The observation transaction can use up to its server deadline before the separate scan admission budget begins, so an end-to-end Cron wall-time bound needs runtime measurement. The SQL remains a proposal; production migration, role provisioning and rollback have not been performed. This does not close C04.6 or C04.G.
