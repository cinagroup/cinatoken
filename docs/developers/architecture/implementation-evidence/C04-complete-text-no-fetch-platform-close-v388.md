## Authority and transaction

The only runtime entry point is `close_complete_text_no_fetch_v388(grant_id uuid, resolution_id uuid, decision_nonce uuid)`, callable by direct `NOINHERIT LOGIN cinatoken_gateway_complete_text_platform_closer`. The caller supplies no amount, units, decision digest, source fact or supplier-cost claim. The function derives those identities from stored rows and computes the decision digest. Its returned receipt is staged until the outer transaction commits; the TypeScript client returns only after COMMIT and connection close acknowledge. An uncertain result must be retried with the same nonce. Each transaction closes one request; batching requests sharing account/window counters in one transaction is deliberately rejected by the exact deferred delta checks.

The platform zero buyer result follows from the controlled send protocol: physical fetch requires a fresh, acknowledged v365 send-start receipt; v370 holds the same request advisory lock, proves the send deadline passed with no committed marker and no contradictory fact, and permanently blocks later custody/start insertion. A marker without a `fetch_invoked` observation remains possible send and cannot enter this branch. These are platform protocol facts, not a provider statement of final zero charges. The v360 quote freezes the platform tariff and reserve ceiling; it does not supply measured actual units for an attempted request. The no-fetch branch needs no actual-use token count.

Under request lock `(348, hashtext(stored request_id))`, v388 joins the one unknown grant, immutable quote, admission and exact v370 resolution. It rejects any send start, non-no-fetch fact, renewal, preexisting buyer log, changed account epoch or extra grant. It locks the account, then all future reservation/window write tables before touching exact hold/window rows. It verifies ordinary identity, all stored Guardrail intents, amounts, states, expiry bindings and active reservation counter sums. Unlimited ordinary budget and zero Guardrail intents are valid.

The function inserts a protected terminal with its PostgreSQL transaction ID and before-state snapshots. The successor to v367's hold trigger allows only the dedicated closer's exact snapshot-to-`settled(0)` transition in that transaction, preserving the existing renewal exception for other open requests. Ordinary `reserved` decreases by its full admitted reserve, every exact Guardrail window loses its corresponding reserve, and spent/settled amounts stay unchanged. The zero request log has `status='error'`, `error_message='verified_no_fetch'` and explicit pricing-audit metadata. A separate `platform_text_no_fetch_closed` version-1 event carries the frozen grant, quote, resolution, selected fact IDs/digests, terminal identity and zero buyer result. It is not a shared-key seller-payment event.

Deferred checks require the complete terminal/log/event/hold/counter set at COMMIT. Missing log/event, partial hold change or wrong counter delta aborts everything. New terminal/outbox rows and their associated buyer log are immutable. The closer has no raw table DML, so calling `SET CONSTRAINTS ALL IMMEDIATE` cannot create a later mutation channel. Calling it before the function inserts companions causes safe transaction failure. New grants/renewals and holder observations after the monetary terminal are rejected under the same request lock. This final decision freezes holder evidence more strictly than v386's egress-only fence. Existing separately authorized provider-bill intake retains its own rules; it is not newly authenticated and gains no power to alter the terminal. An alleged provider bill for a no-start request requires a separate incident/late-evidence path, which is still missing.

## Native evidence and limits

The fixture installs actual PG73 and reviewed dependencies including v368/v371/v372/v380 counter authority and v386. Installation requires the historical grant policy to remain superseded, exact v370/v380/hold trigger identities and selected source-body hashes, and no raw writes on money tables for the legacy buyer or public runtime. The current fixture satisfies this deliberately strict ACL prerequisite. Activation does not revoke unrelated runtime rights to force a pass; an installation with additional user-profile writes must review its exact authority and compatibility before cutover. No formal migration or existing frozen proposal is edited.

The native cases cover four-hold zero closure, unlimited ordinary and zero-total-hold closure; real-client replay; two concurrent closers; caller rollback; deferred COMMIT failure; missing companion rows; post-`SET CONSTRAINTS` DML rejection; epoch/counter/hold drift; possible-send rejection; and a valid holder `fetch_not_called` observation accepted before close and rejected by the exact terminal constraint afterward. Unrelated legacy requests are fixture-seeded, then settled by the actual direct buyer LOGIN and v371 writer while sharing the account and three Guardrail windows. Both transaction orders are exercised with observed lock waits and successful commits. This is SQL-writer compatibility evidence, not execution of the whole Proxy application.

The lost-ACK proxy suppresses a real PostgreSQL COMMIT `CommandComplete` response after the database commits. The client reports uncertainty; a direct retry with the same nonce reads the existing terminal and leaves every amount/event unchanged. This does not simulate a TCP ACK, process crash, Hyperdrive or a deployed connection pool. Deadline shortening and missing-companion corruption use owned-cluster superuser fault injection; runtime principals lack those powers. The report pins both client sources, SQL, fixture, dependencies and proxy. The fixture verifies its source did not change during its final run.
