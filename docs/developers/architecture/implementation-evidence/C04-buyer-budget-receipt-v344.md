# C04 v344: database receipt for v2 ordinary-buyer debit

Status: **review-only; production default off**. No formal migration, remote database, or deployed runtime was changed. This companion installs after the v2 economic producer in an explicitly activated migrator transaction. It does not close C04 as a whole.

## Bypass and contract

The v341 v2 trigger proves that a reservation row reached a terminal state in the event transaction. For an `actual` event without a reservation, it compares `buyer_debit_micros` to the request log charge but has no independent evidence that `users.budget_spent` increased. A runtime LOGIN can therefore insert a same-transaction buyer log, call the v2 producer, and commit an economic event without charging the ordinary-user account. The same missing account proof applies to current-epoch reservation-backed `actual` and `reserved` events.

[The receipt companion](../../../../packages/core/migrations-proposals/postgres/shared-key-buyer-budget-receipt-v2.sql) installs a private, trigger-populated `(xid8,user_id)` account receipt. The users trigger records the **net** `budget_spent` and `budget_reserved_micros` changes over the whole transaction; insert, delete, identity change, or epoch change poisons that transaction's receipt. A deferred v2 event trigger uses the existing private buyer-log xid8 markers to sum **all** v2 debits for that user and transaction. A positive current-epoch debit requires enough net account spend increase; reservation-backed events also require the net reserved-counter decrease. The users trigger rechecks already inserted events after every later account mutation, so switching deferred constraints to immediate cannot validate a temporary debit and then erase it. One account update cannot support two economic events, and an increase followed by a refund in the same transaction contributes zero.

Every new reservation gets a private admission candidate. A deferred verifier marks it `hold_verified=true` only when the same admission transaction increased the buyer's reserved counter enough to cover the entire candidate batch, with matching current epoch and a finite budget. The final account's spent plus reserved amount must fit the current limit, and the reservation must carry that limit. Later account or budget-limit changes in the admission transaction are rechecked if validation ran early. An immediate reservation guard keeps verified admission identity, epoch, limit and reserved amount stable, and blocks deletion; it also protects these fields once a v2 event exists. Unverified candidates do not block legacy, unlimited-budget, or pre-settled reservation inserts; they cannot back a v2 event. Unverified candidates cascade on non-economic reservation rename/delete, while v341's existing settlement marker continues to retain enrolled v2 reservations. Pre-install reservations have no admission receipt and cannot be silently adopted into v2.

**Old-epoch v2 reservation events are rejected**, even with a verified historical admission. A hold in a closed budget epoch proves reserved capacity, not a `users.budget_spent` debit. The PostgreSQL critical writer intentionally skips current-account spend changes when the reservation epoch differs. A separate versioned settlement or adjustment ledger is required before that path can emit v2 economics. Existing v1 event and five-argument producer behavior remains as before; this receipt does not validate v1 debits.

## Remaining production gates

- The runtime role still has broad gateway-table writes, including direct `INSERT` on `shared_key_earnings` and `UPDATE` on `users`. This receipt closes the tested v2 outbox bypass; the legacy direct earning path and later arbitrary balance reversals require role separation or additional immutable ledger policy.
- The private xid8 receipt table grows with budget-field updates and user lifecycle changes. The v345 review-only maintenance candidate proves bounded backfill/pruning on PG18.6; retention policy, production-scale scan/lock cost, scheduling and write amplification remain unverified. Admission candidates also need retention rules after reservations close.
- Existing reservations cannot gain verified admissions retroactively without reviewed historical evidence; drain or reconcile them before enabling v2 events. Old-epoch settlements and post-event late reconciliation need explicit adjustment events and accounting policy.
- `recordUsage` and per-attempt provider-observer facts are not connected to this proposal. The test uses a local runtime LOGIN and synthetic quote/outcome facts; Workers, Hyperdrive, queues, Linux CI, and remote rollout remain unverified.
