# C04 v364 grant result, custody, and recovery protocol (review proposal)

2026-09-25. This specifies a possible PostgreSQL successor to the review-only [v362 attempt grant](../../../../packages/core/migrations-proposals/postgres/complete-text-attempt-grant-v362.sql). It is a source audit and implementation plan, not installed SQL, a deployed holder, a provider bill, or C04 acceptance. The immutable v362 grant remains `unknown`; a new grant-linked record must carry each subsequent fact. The [v363 audit](./C04-v363-grant-result-lease-boundary.md) identified the need for that record and for an all-hold recovery fence.

## Invariants derived from the current SQL

- [v360](../../../../packages/core/migrations-proposals/postgres/authenticated-complete-text-quote-v360.sql) fixes one `max_per_attempt_ceiling_micros` and a three-attempt ceiling; [v361](../../../../packages/core/migrations-proposals/postgres/complete-text-quote-budget-admission-v361.sql) reserves the **same full three-attempt amount** in the ordinary hold, if limited, and each applicable Guardrail hold. The Guardrail count can be zero and the ordinary status can be `unlimited`; the grant still needs a result obligation.
- v362 inserts an immutable possible-send row and sets all existing holds to `dispatched` with an initial 15-minute recovery expiry. Its `send_expires_at` is at most 30 seconds. `hold_recovery_expires_at` cannot authorize a later send. A lost transaction or connection-close acknowledgement does not authorize `fetch` or reuse of the nonce.
- [v353 Guardrail expiry/forfeit](../../../../packages/core/migrations-proposals/postgres/guardrail-budget-lifecycle-login-v353.sql) and [v354 ordinary expiry/forfeit](../../../../packages/core/migrations-proposals/postgres/ordinary-budget-recovery-login-v354.sql) each move an expired dispatched reservation to `expired` at its **full reserved ceiling**. This is conservative forfeiture, not zero-charge proof. They operate independently and cannot be the normal result writer for a v362 request. v354 currently locks a reservation before its user; v362 locks the user before the reservation, so merely adding a late grant check to v354 is insufficient to establish a common lock order.

## Proposed rows and narrowly authorized functions

All new tables are private to the migrator. `cinatoken_gateway_runtime`, the admission LOGIN, old recovery LOGINs, and the gateway Worker get no direct writes. New direct `NOINHERIT` LOGINs for the independent holder, recovery custodian, and platform closer receive only the functions named below. Every `SECURITY DEFINER` function checks `SESSION_USER`, `READ COMMITTED`, a fixed `search_path`, bounded inputs, and server time. A transaction result is usable only after COMMIT and connection-close acknowledgement.

| Record | Keys and required facts |
| --- | --- |
| `complete_text_request_custody_v364` | `request_id` primary key, current `grant_id`, monotonically increasing `lease_epoch`, `holder_run_id`, `mode` (`active`, `recovery`, `terminal`), effective `lease_until`, immutable `hard_deadline`, optional `resolution_id`. This is the mutable custody clock; v362's expiry column stays immutable. It exists even with zero physical budget holds. |
| `complete_text_send_starts_v364` | `grant_id` primary key, request and holder-run identity, lease epoch, server `recorded_at`, hash of the holder's independently frozen physical upload. Its presence means **possible send**, never confirmed provider receipt. It is insert-only and cannot be replayed as a new send permission. |
| `complete_text_result_facts_v364` | Unique `(grant_id, evidence_nonce)` plus kind, evidence-source identity, provider request reference where available, canonical evidence digest, server receipt time, and immutable copy of the grant's quote, route, credential and body commitments. No secret, URL, or raw upload is stored. Same nonce and digest is idempotent; conflicting digest is rejected and audited. Facts include `no_fetch_attestation`, `fetch_invoked`, `transport_unknown`, `provider_zero_charge`, `provider_usage`, and `provider_bill`. A transport error, HTTP status or gateway report alone cannot prove zero charge. |
| `complete_text_attempt_resolutions_v364` and `complete_text_request_terminals_v364` | One resolution per grant and at most one terminal per request. Resolution is `verified_no_fetch`, `verified_zero_charge`, `actual`, or `unknown`; it cites fact IDs and a unique decision nonce. The request terminal cites every grant, the selected charge basis, total buyer debit, budget epoch treatment, buyer log ID, and a typed platform economic outbox event. Late facts never mutate these records. |
| `complete_text_write_tx_markers_v364` | Protected `(request_id, pg_current_xact_id(), operation)` marker with `operation` = `claim`, `lease`, or `terminal`, the relevant grant/epoch/resolution ID, and expected row/counter deltas. Only the corresponding SECURITY DEFINER writer inserts it. Reservation, counter, buyer-log, and outbox guards require the matching marker for grant-linked changes; a caller-set custom GUC is not evidence. Deferred constraint checks verify the complete bundle before COMMIT. |

Suggested entry points and return rules:

1. `record_complete_text_send_start_v364(grant_id uuid, holder_run_id uuid, expected_epoch bigint, upload_sha256 text) -> jsonb`: lock by request, then custody; require the sole current grant, no earlier send-start row, no terminal, a committed active lease, exact grant upload commitment, complete dispatched holds, and `clock_timestamp()` strictly before both lease and v362 send-start deadline with a configured safety margin. The database can check the committed lease epoch; the holder must separately possess its prior COMMIT/close acknowledgement. Insert once. Only the **fresh** `start_recorded` result after its own COMMIT/close ACK permits this holder run to invoke one physical `fetch`; duplicate/lost-ACK replay returns `already_possible_send`, never fresh authority. If the closer holds the same request lock, sees no send-start marker after the deadline, and fences the holder run, it may prove no fetch; the lock makes it wait for an in-flight send-start transaction to commit or roll back. If a marker exists and the holder crashes before reporting, retain `unknown` absent authoritative zero-charge evidence.
2. `append_complete_text_result_v364(grant_id uuid, evidence_nonce uuid, kind text, evidence jsonb) -> jsonb`: holder-only for local send observations; a separate independently authenticated provider-bill adapter must write bill facts. Derive quote, route, credential and body identity from the stored grant rather than accepting those fields from the caller. Bind every fact to the exact holder run, validate bounded shape and evidence digest, insert append-only, and never infer no charge from missing usage. An attested `fetch_not_called` after a send-start marker is insufficient by itself to clear uncertainty after a crash. Result-fact ACK loss is resolved by authoritative primary-key read, not by assuming absence.
3. `renew_complete_text_active_v364(grant_id uuid, holder_run_id uuid, expected_epoch bigint) -> jsonb`: holder-only compare-and-swap. Require the current active grant and live lease, no terminal, valid one-shot send-start, and `clock_timestamp() < lease_until`. Under one request advisory lock, lock custody, user account when applicable, all exact Guardrail reservations and windows in deterministic order, then the ordinary reservation; recheck the v361 intent count/identities/amounts, `dispatched` markers, reserved counters, and numeric bounds. Move **every** physical hold and custody to one `LEAST(clock_timestamp() + interval '15 minutes', hard_deadline)` expiry and increment the epoch, or move none. Return the observed minimum expiry and new epoch only after COMMIT/close ACK. The holder must cancel further upstream reads if its acknowledged lease cannot be renewed; an uncertain renewal ACK grants no extra live time. Renewal does not extend quote, admission or send-start authority.
4. `retain_complete_text_unknown_v364(request_id text, expected_epoch bigint) -> jsonb`: recovery-only, under the same request/row locks. It may run after a lease timestamp has passed because grant-linked legacy reapers are fenced. It changes mode to `recovery`, fences the old holder epoch, and extends all existing dispatched holds together up to `hard_deadline`; it returns **no send right**. A missed epoch or inconsistent/missing hold leaves the request unresolved and alerts an operator. Recovery cannot create a new attempt.
5. `close_complete_text_request_v364(request_id text, resolution_id uuid, evidence_ids uuid[]) -> jsonb`: platform-closer-only. Under the same locks, require a fenced holder, no possible live send, exact grant/resolution coverage, and either independently verified charge evidence or a policy-approved hard-horizon unknown forfeiture. Compute buyer debit from the frozen pricing/usage evidence, never from a gateway claim. For actual debit `B`, require `0 <= B <= v360.three_attempt_ceiling_micros`; above-ceiling evidence enters a separate debt/incident path instead of silent clamping. For unknown forfeiture, set `B` to the full reserved ceiling. In one transaction set the ordinary reservation, if present, to `settled(B)` for verified actual/zero or `expired(full ceiling)` for unknown, decrement its reserved counter and add `B` to the **matching** budget epoch; perform the corresponding transition on every Guardrail reservation/window (`reserved -= ceiling`, `settled += B` in each window); write one buyer log and one typed **platform-grant** economic outbox event; insert the request terminal and protected transaction marker. A zero-hold request still writes terminal/buyer/economic facts. Same resolution ID and digest returns the committed terminal; conflict or partial bundle fails. The current shared-key economic producer cannot represent this grant.

The hard horizon is a product and billing policy input, not a send extension. A proposed 24-hour bound would require the holder to stop any stream before that deadline and the closer to wait until the holder is fenced. Full-ceiling forfeiture is a conservative financial outcome with a user-facing billing consequence, so it needs explicit policy approval before activation. A later provider bill is appended as new evidence and reconciled through a separately authorized adjustment ledger/event; it never rewrites the original terminal, releases its spent capacity in place, or revives the send slot. An amount above the reserved ceiling is an uncovered liability requiring separate handling.

An ordinary budget epoch can change while an SSE or unknown attempt is held. The existing account reset can clear `budget_reserved_micros`; v354 already skips updating a different epoch. The v364 cutover therefore also needs an epoch-transfer liability row in the **same reset transaction**: the old reservation and debit remain tied to the old epoch, while the new epoch starts at zero. Renewal and closer verify this transfer when the account epoch differs; neither subtracts an old hold from a new epoch nor treats the reset as evidence of no charge. Without this reset integration, the protocol must fail closed at epoch drift.

## Reaper and retry cutover

The v353 and v354 explicit forfeit and expiry functions must be replaced in the **same activation transaction** as the custody guards. Their grant-aware branches acquire `pg_advisory_xact_lock(348, hashtext(request_id))` before row locks, then skip any request with a v362 grant; legacy requests retain their prior expiry behavior. The v354 scanner must select candidate request IDs first, take a try-advisory lock, re-read the reservation, then lock the user and reservation in the reviewed order. Protected triggers reject any direct v361-admitted `reserved` -> `dispatched` transition without a private `claim` marker and any enrolled `dispatched` lease or terminal change without a `lease`/`terminal` marker, including old runtime repository writes. These triggers are the race backstop if a pre-check saw no grant. The grant path must likewise fail if a pre-grant reaper won and terminalized a hold. A batch scanner must continue past enrolled requests instead of aborting its whole batch. Direct account/window/buyer writes that could bypass a grant-linked bundle must be revoked or fenced in the coordinated runtime privilege cutover; table triggers on reservations alone do not protect those counters.

The existing `grant_complete_flat_text_attempt_v362` always returns `pending_unknown` after the first grant and requires still-`reserved` holds. It cannot issue attempt 2 or 3 merely because a v364 fact exists. Activation must revoke the v362 entry point and publish a replacement granter that writes the private `claim` marker **before** it changes v361 holds and inserts v362-shaped immutable grant/custody rows in the same transaction; otherwise the new dispatch trigger would reject its own grant. That granter may consume a fresh nonce/slot under the same request lock only when the previous attempt has a committed `verified_no_fetch` resolution, no start marker or bill contradiction, the original quote/admission and route source are still valid, and all original holds remain complete and dispatched. Its same-nonce replay remains non-authorizing. An ambiguous, billed, over-ceiling, or externally visible successful attempt cannot be retried under this minimal protocol. After three verified no-fetch attempts or a final actual/unknown result, close the request atomically. Any broader retry rule needs attempt aggregation and provider idempotency evidence.

## Native PostgreSQL assertions required before installation

Run v360–v362 plus the proposed activation in an isolated PG73-native fixture with separate direct LOGIN connections. Assert all-or-none rows and counters after every COMMIT/rollback, including: holder-only send-start/result/renewal and bill-adapter-only bill facts; lost start/result/renewal/terminal COMMIT or close ACK; duplicate and conflicting nonces; crash before start and after start but before `fetch`; a >15-minute SSE with multiple acknowledged renewals; an expired live lease that recovery retains without reauthorizing send; zero Guardrail and unlimited ordinary cases; one missing/changed/expired/terminal reservation; counter mismatch and integer overflow; account epoch rollover; and an over-ceiling provider bill. Race renewal, recovery, grant, explicit forfeit, both legacy reapers, buyer writer, and closer in both commit orders. Every race must leave either the complete dispatched custody or one complete terminal bundle, never ordinary settled with Guardrail still live (or the reverse). Check that non-grant leases continue to expire and that enrolled rows do not starve a bounded scanner. Verify late-bill adjustment is separate and exactly once. No database fixture alone proves the holder's physical fetch, provider billing, stream cancellation, or fleet cutover.
