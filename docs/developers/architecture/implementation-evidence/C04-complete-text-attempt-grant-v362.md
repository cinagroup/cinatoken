# C04 complete flat-text attempt grant (v362 review)

2026-09-25. [`complete-text-attempt-grant-v362.sql`](../../../../packages/core/migrations-proposals/postgres/complete-text-attempt-grant-v362.sql) is a default-off PostgreSQL proposal after the v360 complete quote and v361 manifest-derived admission. It is not a formal migration or an enabled Chat route. It requires a separately provisioned direct `NOINHERIT LOGIN cinatoken_gateway_complete_text_attempt_granter` and the explicit `cinatoken.complete_text_attempt_grant_activation=reviewed-v1` transaction setting. No remote database, production role, Worker secret, or provider was changed.

## Database claim and durable obligation

`grant_complete_flat_text_attempt_v362(attempt_nonce uuid, claim jsonb)` accepts the precise v361 text claim fields plus `outboundBodyCanonicalSha256`. The function validates the claimed request, quote, candidate, model, route target, endpoint, platform credential ID and ciphertext digest against the immutable v360 manifest; rechecks the live source generation, attestation, endpoint and every active candidate route under conservative source locks; and rechecks the current Key/User/Workspace, BYOK absence, Guardrail configuration, v361 admission, ordinary hold and each Guardrail hold. The amount comes only from the v360 `three_attempt_ceiling_micros`, as persisted by v361. A raw v350/v351 reservation row without a v361 admission cannot authorize this call.

The `preparedRouteSourceSha256` is the distinct TypeScript route DTO digest. It is stored as an **opaque physical-side commitment**; it is not compared with v360 `source_sha256`, which hashes a different JSONB source snapshot. `upstreamUrlSha256`, `outboundBodySha256`, `outboundBodyCanonicalSha256`, `outboundBodyBytes` and the plaintext bearer fingerprint are likewise commitments supplied by the caller. Their format is checked, but PostgreSQL does not prove the actual upload or decrypted secret. The separate holder must recompute and compare them from frozen wire material. In particular, storing a caller's canonical digest does not prove the final-body-to-outbound transformation.

The grant function serializes by request ID and, in one transaction, marks the exact v361 ordinary and Guardrail holds `dispatched`, extends their recovery lease from the server clock to 15 minutes, and inserts an immutable attempt row with `obligation_state='unknown'` before returning `status='grant_recorded'`. The send-start deadline is at most 30 seconds and never exceeds the quote or v361 admission expiry. The insert-only row survives a committed grant whose Worker or connection acknowledgement is lost. The same nonce returns `already_recorded_unknown` and a different nonce returns `pending_unknown`; neither is a fresh send right. The schema bounds attempt numbers to 1–3, but this proposal has no authorized outcome/resolution writer. It therefore issues only attempt 1 while the prior obligation is unknown. A later protocol must prove an outcome before permitting another attempt.

The function result is generated *inside* its transaction. It does not assert that COMMIT or connection close was acknowledged. A future direct LOGIN broker may create the v361 `status='committed', commitAcknowledged=true` receipt only after those acknowledgements and must never turn `already_recorded_unknown` into one. The v362 installation also revokes direct `mark_user_budget_dispatched_v350` and `mark_guardrail_budgets_dispatched_v351` EXECUTE from the admission LOGIN, closing the mark-without-grant side door. Existing opt-in adapters require a coordinated cutover; the current Chat path does not call v362.

## Local evidence and remaining boundary

The [native PG18.6 fixture](../../../../scripts/db/cutover/postgres-complete-text-attempt-grant-v362.native.test.mjs) and [machine report](./C04-complete-text-attempt-grant-v362-report.json) passed **20/20 stages, cleanup PASS**. Cases include activation and role drift rejection, direct-table and old-mark ACL denial, missing v361 admission despite a preexisting ordinary row, the 90,003-micro-unit ordinary and three Guardrail holds, an atomic dispatched/unknown grant, same-nonce lost-ACK replay, different-nonce refusal, parallel LOGIN serialization, immutable obligation, cancellation refusal after dispatch, changed target/ciphertext/method/canonical digest, rolled-back grant with rolled-back dispatch, source drift after admission, released Guardrail hold, source-proven unlimited/no-intent admission, and server-clock Key expiry. The fixture installs proposals in an isolated PG73 database and destroys its cluster; it does not establish Linux CI, deployed Hyperdrive role behavior or provider billing.

**This is not production send authority.** The independent holder that owns the actual plaintext credential and physical fetch does not exist yet, and the actual outbound canonical body transform is still proved only locally in the Worker. The 15-minute dispatched hold can expire while an unknown attempt or long SSE remains; there is no grant-linked renewal, trusted result writer, provider-bill reconciliation, buyer settlement or economic event recovery from this row. The unknown row is a durable obligation to reconcile, not proof that the provider accepted or billed the request. Formal migration, production throughput of the broad locks, D1/MySQL parity, full three-attempt resolution and C04 acceptance remain open.
