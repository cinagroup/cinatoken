After the send deadline, the isolated v370 resolver commits a `verified_no_fetch` resolution linked by request ID, quote ID, grant ID, attempt nonce, claim digest and outbound body digest. This fixture verifies both v370 fence triggers are installed and exercises a rejected late custody insert; the [v370 fence fixture](./C04-complete-text-no-fetch-fence-v370.md) separately exercises the late send-start path. The grant stays `unknown` and all four holds `dispatched` with zero settled micros. No buyer log or economic event is created.

The fixture calls each existing dedicated entry with its real LOGIN and confirms the authorization is present. v354 ordinary recovery and v353 Guardrail forfeiture were launched together; both reject the grant-linked request with the exact `complete_text_enrolled_hold_v366` constraint and roll back. This does not establish a deterministic database lock race. The exact v368 buyer writer rejects a request with a v362 grant under `complete_text_enrolled_buyer_v368`. The v367 renewer requires a matching send start and can only extend leases; the v370 resolver only replays its fence. Separate raw DML attempts show resolver/runtime ACL denial and the v367 hold trigger's refusal even to the fixture migrator. Those DML checks test ACL and trigger boundaries; they do not substitute for a missing business function. The final database state still contains one no-fetch resolution, one unknown grant, one dispatched ordinary hold, three dispatched Guardrail holds, and no buyer log.

This fixture installs v368 to test its authorized buyer call but does not install the v372/v376/v380 legacy buyer branch. The [v379 native proof](./C04-complete-text-admission-buyer-v379.md) covers v380 in one database. v382 pins the v380 SQL source and observes that its buyer-only admission fence does not authorize a platform closer.

## Missing successor

A platform no-fetch closer needs a separately authorized zero-charge fact. The v370 send fence alone does not prove Provider billing is zero. A dedicated platform closer must match that fact to the immutable quote, admission, grant, send custody/start history, result and bill observations, and budget epoch. In one transaction it must append a unique platform terminal and typed outbox fact, release the ordinary and all three Guardrail holds, decrement their reserved counters, and bind the terminal, outbox and account changes to the same transaction ID. It must fail closed on any possible send, bill contradiction, missing fact, replay conflict, limit drift or partial hold set. A committed terminal reader is needed for an unknown commit acknowledgment.

The successor must replace the v367 hold trigger atomically with a narrowly scoped exception for that dedicated platform closer, tied to the terminal row and transaction ID. It must keep v380's legacy buyer exclusion and raw financial DML denial. Before rollout, a native proof must cover concurrent close and late bill/fact races, transaction rollback after a late write failure, replay and receipt linkage. v382 does not create this closer or infer zero Provider cost from absent send-start rows.
