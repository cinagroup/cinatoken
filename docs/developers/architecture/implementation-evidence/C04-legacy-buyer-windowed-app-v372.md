The [native application fixture](../../../../scripts/db/cutover/postgres-legacy-buyer-windowed-app-v372.native.test.mjs) reports [PASS, cleanup PASS, 20/20 stages](./C04-legacy-buyer-windowed-app-v372-report.json) against local PostgreSQL 18.6. ## Implemented transaction

The [v372 helper](../../../../packages/core/src/db/postgres/legacy-buyer-windowed-transaction-v372.ts) verifies `current_user` and `session_user` are the dedicated buyer LOGIN and the transaction is `READ COMMITTED`, then takes the request advisory lock before the critical writer's API-key `FOR UPDATE` lock. The opt-in writer rejects recovery, mismatched request IDs or reasons, non-actual modes, BYOK, unsuccessful logs, non-v2/non-actual economic facts and inconsistent micro amounts before opening the transaction.

Within one existing Drizzle outer transaction, the writer locks the API key, inserts the append-only request log, invokes v371, checks the staged response, derives the audit baseline from the database-locked account and settled hold, creates the real v2 economic event and receipt, then writes provider attempts, public model stats and the user audit. The v371 function derives the debit from the inserted log and performs both the v368 held transition and applicable unreserved Guardrail window updates. The opt-in branch skips the writer's direct ordinary and Guardrail financial mutations. A failure after the event, including a late audit error, rolls the complete transaction back. The helper never acknowledges COMMIT. A unique-key replay is rejected pending a committed terminal-read protocol; it never debits again.

The audit query reads the account and settled hold after v371 while its account row lock is still held. It inverses the exact v368 `budget_spent` and reserved counter deltas to create complete before/after user snapshots; caller-supplied pre-state and snapshots are ignored. This query uses ordinary `SELECT`: the dedicated buyer role has no raw `users UPDATE` privilege. Two already admitted requests for one user with the same stale `beforeSpent` value, distinct API keys and distinct database connections both commit with ordered authoritative audit snapshots. The same-transaction baseline is covered in the [v374 evidence](./C04-legacy-buyer-audit-baseline-v374.md).

## Native composition and privileges

The native fixture installs all 73 formal PostgreSQL migrations, the exact v368 held function body, v371 and the [v372 ACL successor](../../../../packages/core/migrations-proposals/postgres/complete-text-legacy-buyer-window-acl-v372.sql), the real v2 economic producer and budget receipt proposals, v347/v348/v349 buyer-login split, and v350 ordinary admission. It uses a minimal v362 grant table, not the entire v351–v368 proposal chain. A dedicated admission LOGIN creates a genuine verified hold receipt before the application writer runs; the writer does **not** create its own admission. The positive fixture checks the request log and receipt share the same transaction ID, with one held debit, applicable unreserved user/Workspace/API-key window debits, audit, stats and v2 event committed together. The fixture also checks API-key `FOR UPDATE`, log `INSERT`, event producer execution, replay rejection, unsupported mode rejection, concurrent same-user baseline, forged caller snapshot rejection, clamped-balance rollback and late failure rollback.

The fixture manually grants the buyer LOGIN the app privileges it needs: `api_keys SELECT, UPDATE`, `users` and reservation `SELECT`, request-log `SELECT, INSERT`, stats `SELECT, INSERT, UPDATE`, audit and provider-attempt `INSERT`, and v2 producer `EXECUTE`. It then checks raw financial table updates remain denied. The later [v374 application ACL proposal](./C04-legacy-buyer-windowed-app-privileges-v374.md) narrows those table grants to the required columns and closes runtime Guardrail DML in a separate native fixture. The v372 positive result still depends on temporary fixture grants; neither proposal is a formal installed production role migration.

The earlier broad [runtime grant script](../../../../scripts/db/cutover/grant-postgres-runtime.ts) would otherwise regrant runtime `EXECUTE` on v371. The new review-only ACL successor revokes it, and the grant script now conditionally reapplies that precise revoke on rerun. The fixture reruns the broad grant script and verifies `has_function_privilege(runtime, v371, EXECUTE) = false` and `has_function_privilege(buyer, v371, EXECUTE) = true`; the runtime direct call is denied by SQL privilege (`42501`), rather than only by the function's internal guard. The successor remains a proposal, not a formal migration.
