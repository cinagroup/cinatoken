## 为什么需要这个场景

若新消费者已经提交，旧写入可能仅因重复日志 ID 而失败，不能单独证明租约隔离。本轮在新消费者完成 CAS 认领、尚无日志/回执时暂停其事务，然后释放旧执行者。旧事务实际调用原生 SQLite batch，必须得到 SQL 错误 `Settlement recovery lease invalid`，不能用人为抛错或重复键拒绝替代。

## 实现边界

新增独立 `images-fencing-gateway.ts` 与工厂，服务器固定生产者租约 5 秒、最多 40 次探针轮询；旧 staging 默认 20 次与原恢复入口 30 秒租约不变。5 秒不是生产建议，40 × 500 ms 仅为定时器等待预算，还含 D1 I/O，不是 20 秒硬墙钟上限。

探针增加有限模式 `before-fence`，必须命中精确合成租户和已布置的单次 CAS 行。只有真正租约 SQL 错误才记 `stale-lease-rejected`；其他 batch 错误记 `unexpected-batch-error`，不存原始错误。普通 staging 入口拒绝该模式；请求体、请求头或 binding 不能开启服务器测试配置。

配置生成器只切换独立 staging main，保持原有 9 个绑定及封闭入口，拒绝公共路由/预览和消费者能力注入。未修改财务算法、Core、三份 SQL 草案、生产入口或真实恢复消费者。

按 Workers 最佳实践与 Wrangler 技能，使用请求所有的有界探针、独立候选入口、离线打包和精确生成绑定核验。本轮没有发布或改变云资源。

## 本地证据

测试使用完整 Images gateway、三份实际 SQL 草案与真实 SQLite 事务适配器。生成和编辑各覆盖四种情况：

| 场景 | 断言 |
| --- | --- |
| 旧租约有效 | 竞争恢复无法认领；旧执行者正常提交一次 |
| 旧租约过期，无新认领 | 旧 batch 被租约检查拒绝；后来消费者补齐一次 |
| 新消费者持租约、尚未提交 | 旧 batch 被拒绝，12 组财务/租约投影不变；新消费者随后提交一次 |
| 新消费者随后晚期审计失败 | 真实事务整体回滚、pending 退避 10 秒；后来认领再成功一次 |

新消费者使用实际 `createUsageRecoveryHost`，验证提前登记 waitUntil、同实例重入 busy、在途逻辑容量持有 64 MiB 与结束后释放。它不是物理内存或跨实例互斥证明。新消费者的暂停点是测试侧 batch 包装器，**真实 Worker 消费者侧有界暂停尚未实现**。

测试通过本地 fixture 推进数据库时钟；这不是云端自然租约到期证据。所有成功路径最终日志、回执、费用审计和推理 attempt 各一份，只发生一次上游调用，预留归零；重复恢复无变化。新消费者失败后的最终 job revision=5、attempts=3、receipt lease_revision=4。
