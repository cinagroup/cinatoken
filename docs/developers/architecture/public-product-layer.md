# 公开产品层架构与 MVP 契约

本文定义 cinatoken 公开产品层的版本化边界。目标是把现有 Gateway、模型目录、用户门户与管理控制台组织成统一产品体验；页面结构可参考成熟 AI 路由市场，但品牌、素材、文案、数据与实现均保持 cinatoken 自有。

## 1. 边界与原则

- `https://cinatoken.com` 承载公开发现、普通用户账户中心与管理员控制台。
- `https://api.cinatoken.com` 承载公开目录查询和已认证推理 API。
- 公开页面只显示数据库中的真实模型、协议、路由组和可公开价格；没有数据时显示空状态，不生成示例销量、调用量、延迟或可用率。
- 普通用户继续由 CinaAuth 登录并使用 `/account/*`；管理员在同一身份体系内额外获得 `/admin/*`，不得建立第二套账户或权限来源。
- 供应商密钥、用户 API Key 全文、上游地址、内部路由目标、成本价和原始请求正文均不是公开目录字段。
- 公开页面沿用现有品牌资源、设计 token、四语言消息与 light/dark/system 模式。

### 浏览器登录与会话恢复

首页、公开导航中的用户中心与控制台入口直接启动 CinaAuth 弹窗，原页面保留；普通点击无需先进入独立登录卡片。直接访问受保护 URL 仍提供登录按钮（浏览器需要用户点击才能可靠打开弹窗），Ctrl/Command 点击保留原生新标签页行为，弹窗被拦截时使用整页 OIDC 登录。

- 根布局的 `CinaAuthPopupProvider` 统一管理当前页面的授权事务，重复点击只尝试聚焦已有弹窗。跨域 COOP 可能把仍打开的窗口报告为 `closed`，不能据此取消或重建授权事务。等待上限为 10 分钟，并提供取消操作。
- 每次授权使用独立窗口名和按随机 OIDC `state` 隔离的临时 HttpOnly Cookie，避免不同标签页覆盖 PKCE/nonce。回调必须验证 HMAC、期限和精确 `state`，只清理自身事务；兼容上一次部署尚未完成的旧 Cookie，未知或不匹配回调不会取消其它登录。最终登录身份仍由同一个浏览器会话 Cookie 共享。
- 弹窗 UUID 保存在签名 OIDC 事务中。回调通过同源消息、localStorage 或 BroadcastChannel 回传不含令牌的结果，再自动关闭；回调 HTML 使用 nonce CSP 与 `no-store`。原页面必须再次请求 `/api/user/me` 或 `/api/auth/check`，确认 HttpOnly 会话后才导航。
- 已有有效会话可在登录入口直接复用，避免管理员进入普通用户中心时被新建的门户会话覆盖。控制台复用仍实时检查 CinaAuth 管理角色；注册流程不复用现有会话。
- 页面只把明确的未认证结果视为会话失效。连接错误、5xx 或不合法的成功响应保留已显示的登录状态，并允许重试；浏览器会话检查最多等待 15 秒。CinaAuth 管理角色服务暂时不可用时，本地有效的控制台会话可显示降级状态，但受保护的管理 API 仍独立复验权限并拒绝无法验证的请求。
- 会话期限仍为普通用户 24 小时、管理员 8 小时；本轮不引入无限续期，也不在浏览器存储令牌。
- 桌面与移动门户、管理台统一请求 `/api/auth/logout`。只有服务器明确确认成功后才显示已退出；5xx、断网或无效响应提供重试。服务端撤销浏览器携带的统一与旧版 Cookie 的全部不同令牌（门户/管理两类记录），再清理会话、工作区偏好及未完成授权 Cookie。`__Host-` 授权 Cookie 的过期响应也保留 `Secure`、`Path=/` 且不设置 Domain，避免被浏览器拒绝清理。任一存储撤销失败不会伪报成功。
- 登录和退出通过 BroadcastChannel 与 storage 事件同步其它标签页；事件不含用户信息或令牌，登录事件仅触发服务器复验。退出事件使当前页面旧请求失效，迟到的已登录响应不能恢复已退出界面。无关 Cookie 的编码错误不影响有效登录 Cookie。

本地验证包含桌面/手机入口、COOP 跨源分离、重复点击、取消、超时、禁用 localStorage 时的 BroadcastChannel 完成、伪成功消息不能绕过服务器会话、刷新后恢复、503/无效响应保持状态及 401 清除状态。授权 HTTP 路由测试覆盖并行 Cookie 签发、拒绝授权时的定向清理与未知回调隔离；退出浏览器测试分别禁用 storage/BroadcastChannel，覆盖服务器失败提示、跨标签页同步和迟到响应。隔离浏览器 Cookie 存储测试复现了缺失 Secure 时的清理失败，并验证修复后的过期响应能够真正移除授权 Cookie。浏览器验证使用本地身份与会话响应 fixture；真实 CinaAuth 账号、生产 Cookie 与 Cloudflare 环境的端到端验收需在部署后执行。

## 2. 分阶段页面范围

| 阶段 | 路由 | 目标 | 认证 |
| --- | --- | --- | --- |
| Phase 2A | `/` | 公开首页与产品入口 | 无 |
| Phase 2A | `/models` | 搜索、过滤、排序与浏览真实模型目录 | 无 |
| Phase 2B | `/models/[vendor]/[slug]` | 模型能力、协议、路由组与公开价格详情 | 无 |
| Phase 2B | `/providers` | 供应商公开能力与可用模型汇总 | 无 |
| Phase 3 | `/compare` | 对比最多四个已发布模型的上下文、价格、模态与协议 | 无 |
| Phase 3 | `/chat` | 使用用户临时输入的 Gateway Key 调用已选文本模型 | 页面无认证；请求需 API Key |
| Phase 3 | `/rankings`、`/benchmarks` | 基于达到隐私阈值的真实聚合数据展示调用量、可靠性与延迟 | 无 |
| 已有 | `/account/*` | Key、活动、收益、提现、NFT 与设置 | CinaAuth |
| 已有 | `/admin/*` | 供应商、模型、路由、用户、审计与运营管理 | 管理员能力 |

未实现的路由不得出现在主导航中作为可用功能。可以在发布说明中标记后续阶段，但不可渲染伪功能页。

## 3. 数据真源

| 页面字段 | 真源 | 公开规则 |
| --- | --- | --- |
| 模型 ID、名称、上下文、最大输出、模态、发布日期、标签 | `models` | 仅活动模型 |
| 支持协议、推荐协议、路由组 | `route_pools`、`route_targets` 与目录发现服务 | 只公开聚合能力，不公开内部目标 ID |
| 面向用户的价格 | `models.pricing_profile` | 只公开标准/用户价格，不公开供应成本与密钥分成 |
| 供应商名称、支持模型数量 | `providers` 与活动路由聚合 | 不公开 `api_key`、`base_url`、请求头或内部配置 |
| 调用量、延迟、可用率 | `public_model_daily_stats` 分片日汇总 | 请求日志写入事务内同步维护；公开请求禁止回退扫描原始日志，且达到最小样本阈值后才公开 |
| 用户个人活动 | 当前用户范围内的请求日志聚合 | 仅本人可见，服务端强制 `user_id` 过滤 |

模型目录首批复用现有 `GET /catalog/models`。该端点返回真实活动路由发现结果，是 `/models` 的唯一初始数据源；响应中的 `billing_currency` 来自规范化后的 `system_config.BILLING_CURRENCY`，公开定价不假定固定为美元。

## 4. API 演进契约

| 状态 | 接口 | 用途 |
| --- | --- | --- |
| 已有 | `GET /catalog/models` | 公开模型目录 |
| 已实现 | `GET /catalog/models/:vendor/:slug` | 单模型公开详情；响应经过目录字段白名单处理 |
| 已实现 | `GET /catalog/providers` | 供应商公开聚合；只从已发布模型派生 |
| 已实现 | `GET /catalog/stats/models?range=7d\|30d\|90d` | 已发布模型的隐私阈值聚合指标 |

Web 同源边界还提供两个只供页面使用的 BFF 路由：

- `GET /api/public/stats` 转发并再次解析公开统计响应，避免浏览器跨源访问；只接受 `7d`、`30d`、`90d`。
- `POST /api/public/chat` 只接受 OpenAI 兼容的 `model` 与文本 `messages`，强制非流式调用并转发请求头中的 Gateway Key。密钥仅存在于当前 React 页面内存和单次请求中，不写入 cookie、localStorage、日志或服务端存储。

Cloudflare 部署中，Admin Worker 通过 `CINATOKEN_PROXY_SERVICE` Service Binding 读取目录并转发 Chat，避免同账户 Worker 重新经过公网自定义域名、WAF 或 Access 策略。Node/Docker 与本地开发仍回退到 `CINATOKEN_PUBLIC_API_ORIGIN`。Service Binding 名称由 `PROXY_WORKER_NAME` 同步生成，不得在租户配置中写死。

公开目录接口必须满足：

- 无认证读取，响应不得包含秘密或内部路由目标。
- 列表支持稳定排序；新增过滤参数时保持旧客户端兼容。
- 服务端响应允许短 TTL 缓存；用户私有数据和管理员数据使用 `private, no-store`。
- 空数据返回合法空集合，不使用硬编码演示数据补齐页面。
- 页面必须区分“网关不可用”“网关正常但尚未发布模型”“筛选后无匹配结果”三种状态，避免把首发配置缺失误报成系统故障。
- 公开聚合必须定义时间窗、样本阈值和失败样本口径。
- 公开模型统计只允许读取最近 90 天的 `public_model_daily_stats`。该表按 UTC 日期、模型和 16 个稳定分片累计请求数、成功/失败数、输出 token 与延迟样本；D1、PostgreSQL、MySQL 迁移会一次性回填最近 90 天。
- `GET /catalog/stats/models` 使用只包含规范化 `range` 的 Cache API 键；缓存未命中时才调用 `PUBLIC_STATS_RATE_LIMITER`。限流拒绝返回 `429`，限流绑定故障返回 `503`，两者都不得查询数据库或写入缓存。
- Node/Docker 运行时使用进程内、最多三个规范化 range 键的 60 秒缓存、固定窗口限流和 single-flight；并发冷请求只产生一次统计加载。多副本部署仍应在入口层增加共享限流。
- `/rankings` 与 `/benchmarks` 展示的是 cinatoken 网关观测到的运营指标，不是模型智能、知识或基准测试分数。
- Chat BFF 的请求体上限为 12 MiB，最多 50 条消息、合计最多 100,000 个文字字符；图片仅接受 PNG/JPEG/WebP/GIF Data URL，单张最多 4 MiB、单次会话最多 4 张且合计最多 8 MiB。上游 SSE 使用 `no-store, no-transform` 并直接透传响应流，不在 Admin Worker 中整包缓冲。
- `/chat` 的浏览器本地会话默认关闭；启用后只保存文字记录和模型 ID，API Key 始终仅在页面内存中，图片字节也不进入 Local Storage。模型回复通过不启用原始 HTML 的 GFM Markdown 渲染，并禁止模型 Markdown 触发远程图片加载。

## 5. 访问控制与路由规则

- 公开路由白名单以显式 helper 维护并有单元测试；不得用宽泛前缀把 `/admin` 或未知路径变为公开。
- `/account/*` 可以在认证外壳之外加载，但实际数据访问必须由 PortalGate 与服务端会话共同保护。
- `/admin/*` 每次进入和每次 API 调用都校验实时 `admin.console` 能力；前端隐藏入口不能替代服务端授权。
- 普通用户登录后的默认落点为 `/account`；管理员可进入同一账户中心，并额外切换到管理控制台。

## 6. 上线前安全门槛

以下项目属于公开产品层上线的阻断条件：

1. 用户 API Key 使用不可逆摘要查找，只在创建时返回一次全文；列表与日志只显示前缀/指纹。
2. 供应商与共享上游密钥使用带版本的 AES-GCM envelope，并支持受控轮换。
3. `REQUEST_BODY_LOGGING` 默认 `off`；只有显式设为 `redacted` 时才写入既有脱敏/截断结果。
4. 请求日志、统计与导出不得泄露请求正文、身份、完整 Key、上游地址或供应商凭据。
5. 所有公开查询有输入边界、分页上限、缓存策略和滥用防护；匿名请求不得触发原始请求日志的全范围分析扫描。

## 7. 验收标准

- 未登录用户可访问首页与已发布的目录页，不被重定向到 `/dashboard`。
- 普通用户登录后进入 `/account`，无法访问管理员页面或 API；管理员可使用同一账户进入两套界面。
- `/models` 在桌面和移动端均能搜索、过滤、排序；刷新和复制 URL 后状态可恢复。
- `/compare` 可通过 URL 恢复模型选择，并限制为最多四个真实目录模型。
- `/chat` 不持久化 API Key，合法调用、缺少 Key、畸形请求与上游不可用状态均有明确结果。
- 排行与网关基准只展示至少 20 次请求的已发布模型聚合，且不返回用户、成本、路由目标、供应商错误或 Key 数据。
- 页面显示的数据可逐项追溯到公开目录响应；空库、部分字段和上游接口失败均有明确状态。
- 所有新增 UI 文案在 `en`、`zh`、`ja`、`ko` 四个 locale 中键集合一致。
- light/dark/system 模式、键盘操作、可见焦点、语义标题和基本屏幕阅读器名称通过渲染检查。
- Proxy 与 Admin 类型检查、单测和生产构建通过；桌面与移动截图完成同视口参考对比。

## 8. 发布顺序

1. 固化本契约并落下日志与密钥安全基线。
2. 发布 `/models` 与显式公开路由白名单，继续复用 `GET /catalog/models`。
3. 扩展模型详情与供应商公开 API，再发布对应页面。
4. 加入对比、Chat 与真实聚合分析；每个阶段独立通过权限、隐私和渲染验收。
