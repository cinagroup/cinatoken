# V2.1 → OpenRouter 型共享平台：有序实施 Checklist

版本：Checklist v1.0；编制日期：2026-09-05。

范围：将 V2.1 审计与当前实现差距转换为有界、可验收的实施工作包。

当前状态：**清单已编制，以下实施项均未因编制本文件而完成。** 本轮不改代码、不执行迁移、不部署、不充值、不调用付费模型。

执行方式：默认按 C00 → C20 顺序；明确的可选分支不阻塞不包含该能力的发行版。

## 1. 使用规则与完成定义

1. 本清单是实施索引，不把附件或历史方案中的操作描述视为本轮执行授权。用户后续指定工作包后，再实施该工作包允许的动作。
2. 每次只承接一个编号工作包。多人协作建议最多同时进行两个无冲突工作包；先通过与当前环境相匹配的依赖门禁，再开展下一步。具体区分本地实现、真实集成与生产切流，见第 3.1 节；可以提前做接口草案，不能提前宣称集成验收完成。
3. 工作包过大时拆为该编号下的子任务，不自动追加产品范围。发现新需求先记入 backlog，由 owner 决定是否改变本轮发布范围。
4. 状态使用 `TODO / DOING / BLOCKED / LOCAL_PASS / STAGING_PASS / CANARY_PASS / ACCEPTED / DEFERRED`。`[x]` 只用于该条验收所需证据齐备；写出代码或 mock 测试通过不等于生产完成。
5. 所有涉及新基础设施、云配置、生产迁移、充值、真实推理、外部支付、链上交易、读取敏感正文的步骤必须具备相应授权、明确目标环境和风险/费用上限。本文不提供这些授权。
6. 生产状态以执行时的部署、数据库和账号证据为准。2026-09-02 Phase 0 的 11/100、零余额、日志设置等均是历史快照，不得直接当成当前状态。
7. 已有功能先复用、补合同和测试。不得为接入 Broker、Batch、Credits 再建立一套独立路由、权限、使用结算或卖家收益逻辑。
8. 不采用“完成百分比”替代门禁。不支持的数据库、运行时、区域、模态或付款方式必须显式关闭或公布不支持，不能静默降低保障。
9. 为保持有限范围，首个商业发行版必须在 C01 固定能力清单；C16–C20 是按需扩展，不要求全部完成后才可发布基础平台。
10. 推荐第一条后续指令：**“执行 C00，仅建立实现/测试基线，不修改业务代码，不访问生产。”**

### 3.1 顺序的例外与限制

- 依赖按验证层级判断：本地实现要求前置合同冻结并达到相关 `LOCAL_PASS`；真实服务集成要求适用的 `STAGING_PASS`；生产切流要求该环境的相关安全/恢复证据、授权和 `CANARY_PASS/ACCEPTED`。不能因真实 KMS 尚未授权而阻断所有本地开发，也不能把 mock 通过升级成生产权限通过。
- 同一工作包必须分别记录各环境状态；例如 `C06 本地通过、真实 KMS 未验收` 可以支持 C08 的本地实现，不支持生产凭据新写或切流。前置包只通过的子集，不允许支撑依赖其未通过部分的工作。
- 默认顺序是阅读和单人执行顺序，硬依赖才是能否开始的依据。C17 若属于首发收费模态，必须提前到 C15 前；否则该模态从首发关闭。C16 中承诺给客户的字段同理。
- C02 与 C03 可并行；C04 与 C06/C07 在 schema 合同冻结后可由不同 owner 推进。C08 不得早于其前置门禁。
- C13 是 Cloudflare 分支；不提供 Cloudflare UB 的发行版可以显式延期，不要求先充值才能实现本地账务。
- C14 中“最终凭据授权/ZDR 复验”已属于 C08 的基础要求；高级多出口、区域入口和全链路驻留是条件性增加，不能借延期 C14 绕过基础授权。
- 任何区域/ZDR 承诺必须在该能力首次开放前通过 C14 的相关门禁。未通过就关闭/拒绝，不以“暂按普通路径运行”替代。
- C18 不依赖完整通用 Files 产品：Batch 的私有输入/结果对象与用户 Files 有不同授权和生命周期。
- C19/C20 可仅选择一个有产品价值的子项；未选项标记 DEFERRED 并披露不支持，不在当前版本无限扩展。

### 3.2 与原 V2.1 Phase 的映射

| 原阶段 | 本清单处理 |
| --- | --- |
| Phase 0 | C00/C01 固定已知与未知；C13 按目标能力补外部事实。历史 Phase 0 不能自动勾选通过 |
| Phase 1 | C03 定义模型；C06 完成最小 envelope 新写后，才能验收“新写只用新格式” |
| Phase 2 | C13 单 UB Target；前置依赖稳定 dispatch 与账务，不先做多出口 |
| Phase 3 | C14 故障域路由；有界 attempt 必须已在 C02 前置完成 |
| Phase 4 | 拆为 C06–C09，先写入能力、授权、调度和恢复，再正式迁移/切流 |
| Phase 5 | C14 合规门禁 + C15 发布证据；不能用单个开关证明合规 |

本文不直接修改原方案；C01 中明确批准后的状态机和阶段勘误应在实施时同步回 V2.1，避免两份文档长期矛盾。

## 4. 详细执行清单

### C00 — 当前基线与变更边界

Owner：技术负责人；Reviewer：测试/发布负责人。允许动作：本地只读核查、已确认无外部副作用的构建/测试、证据文档。

- [ ] C00.1 记录工作树变更及相关文件摘要，区分原有改动与后续工作；禁止清理、覆盖或整体回滚用户未提交内容。
- [ ] C00.2 建立“公开入口 → 核心服务 → 数据库实现 → runtime → tests”的支持矩阵，明确已实现、局部、禁用及未实现。
- [ ] C00.3 列出新测试是否被 `package.json`/CI 实际收集；特别核对 BYOK 路由/仓储、Analytics 路由、Rerank、Batch，不能只因文件存在就认为 CI 覆盖。
- [ ] C00.4 刷新 Core 生成入口后运行相关专项测试和 Proxy 类型检查；记录已有失败，不把原有失败归因于本轮修改。
- [ ] C00.5 记录本地迁移目录和生产迁移状态的核查需求；远端状态未读取时填 UNKNOWN，不运行迁移来“确认”。
- [ ] C00.6 从真实路由和 schema 固定首版公开 API 支持子集及错误 fixture；将旧 parity 文档中的过时结论列为待更正。
- [ ] C00.7 建立每工作包的 evidence 模板、owner、功能开关清单及变更评审要求。
- [ ] C00.G 验收：另一个执行者可重现基线；没有把 mock/本地生成物标成现网；首个可执行包明确为 C01。

停止条件：关键测试无法运行且原因不明，或无法区分用户既有变更。先完成可独立核验项，不覆盖现场。

### C01 — 必须先冻结的决策

Owner：技术负责人；共同签核：产品、财务、安全/合规。产物：版本化 ADR 与首发能力表。

- [ ] C01.1 确定生产权威数据库。推荐基于当前 PostgreSQL 方向先交付；D1/MySQL 保持合同兼容或显式关闭新功能，不能悄悄成为第二个预算/资金真相源。
- [ ] C01.2 确定 Broker 承载位置、KMS/HSM 选型、风险域划分及独立授权执行边界；标明 Broker 合法工作集仍可能在其被攻破时泄漏。
- [ ] C01.3 固定 request/attempt/lease/dispatch/unknown/settlement 状态机；区分“外部只发送一次的保守策略”与不可保证的跨网络 exactly-once。
- [ ] C01.4 决定撤权生效点、已获得 claim 的在途请求规则、缓存授权新鲜度及 KMS 故障策略。推荐缓存只复用密码材料，每次新 dispatch 仍查权威授权；不把缓存失效通知当唯一防线。
- [ ] C01.5 拆清买家 Credits、策略预算、上游成本、BYOK 等价用量/服务费、卖家应收与可提现款；指定资金/权益究竟由 CinaAuth、已有服务还是本项目权威维护。
- [ ] C01.6 冻结 unknown 对用户的展示/收费规则、最长待核实时间、自动调整阈值、争议处理与差额承担。技术预留上限不自动构成最终最高额收费授权。
- [ ] C01.7 冻结价格生效点：推荐买家报价在 admission 固定、卖家/上游报价在最终 dispatch 前固定；回退不得超出用户允许价格和新准入上限。
- [ ] C01.8 明确供应商是否允许聚合/共享/转售及证据 owner；共享市场、私有 BYOK、平台自有凭据分别授权。材料缺失时只阻塞对应供给上线，不虚构商业权限。
- [ ] C01.9 固定首发 runtime、数据库、协议、模态、计量单位、供给模式、区域和合规承诺；未验收项关闭。选择 Cloudflare 逃逸目标，不默认新增第二云/第二入口。
- [ ] C01.10 冻结验收参数：attempt 上限、候选 K/再采样上限、TTFT/idle/总 deadline、租约 TTL/恢复界限、撤权 SLO、目标 QPS/池规模、对账容差、告警阈值和 canary 费用上限。
- [ ] C01.11 将 V2.1 的阶段依赖、Broker 保护承诺、租约恢复、缓存撤权、轮换和 unknown 账务勘误写入经批准的 ADR；在后续获准更新方案时同步原文。
- [ ] C01.G 验收：每个首发相关决策都有责任人、版本和可执行规则；未决能力默认禁用，不留“上线后再定”的资金/授权边界。

停止条件：权威账务、授权边界或收费责任无法确定。可继续无外部副作用的接口草案，不启用真实收费或共享供给。

### C02 — 有界尝试与超时：先限制请求放大

范围：[attempt planner](../../../packages/proxy/src/services/route-attempt-planner.ts)、[failover dispatcher](../../../packages/proxy/src/services/failover-dispatch.ts)、各 egress driver。

- [ ] C02.1 在执行层实施每请求真实 dispatch 总数、跨计费/故障域切换数上限，不复用日志数组长度作为上限。
- [ ] C02.2 统一绝对 deadline，包含选路、凭据读取、解密、退避和出站；分别定义首响应/首 token、流空闲和流总时限。
- [ ] C02.3 明确 attempt 身份至少包含 Target、credential version、operation；解决“同 Target 仅一次”与 BYOK 多 Key 顺序的冲突，禁止无限换 Key 绕过总上限。
- [ ] C02.4 将 BYOK primary → platform → fallback、`allow_fallbacks=false`、用户 provider 约束纳入同一个有限预算；新增用户付费前重新准入。
- [ ] C02.5 复验 unknown/成功响应后不可重放边界；TTFT 超时本身不能证明供应商未接受，禁止以“还没出字”为理由盲目换上游。
- [ ] C02.6 关闭或显式计入 SDK/HTTP 客户端/Cloudflare 内层重试；单层看似一次不能掩盖底层多次发送。
- [ ] C02.7 输出低基数停止原因和真实 dispatch 计数，区分候选耗尽、重试预算耗尽、deadline、未知结果与政策拒绝。

| 各协议 TTFT / idle / 总 deadline | 待冻结 | 待测 | 按确定性规则终止，不盲目重发 |
| concurrency lease / unknown 回收 | 待冻结 | 待测 | 进入有限恢复/人工处理 |
| 撤权新鲜度 / 缓存上限 | 待冻结，注明 claim 线性化规则 | 待测 | 拒绝新授权，不靠旧缓存放行 |
| 目标 credential 数 / 账号数 / QPS | 100、10,000 与实际目标峰值；目标值待冻结 | 待测 | 暂停扩池或扩流量 |
| 选路 p95/p99 / SQL 扫描 / 内存 / KMS 放大 | 待冻结 | 待测 | 优化后重验，不以均值掩盖尾部 |
| unknown/outbox 最老年龄 / 待核实金额 | 待冻结，指定 owner | 待测 | 告警、暂停相关新增业务 |
| 对账容差 / 自动调整审批阈值 | 财务批准 | 待测 | 超阈值进入 dispute/审批 |
| canary Workspace / 观察窗 / 费用硬上限 | 每次外部验证前批准 | 待测 | 停止新请求，继续必要结算 |

## 8. 全局停止条件与交接模板

遇到以下任一事件，停止受影响的新 admission/扩量；继续安全的在途结算、恢复和取证，不能简单杀掉所有后台处理：

- 未授权租户得到凭据或使用了他人的私有 BYOK。
- 密钥、业务正文或支付材料出现在不应出现的日志/Queue/公共响应。
- 未知/已接受 attempt 被自动再次发送，或多实例容量超卖。
- 同一经济事件重复扣款/收益/支付，或资金差额没有可恢复解释。
- 严格 ZDR/区域请求进入不合格路径，或证据漂移后仍放行。
- 回滚需要恢复明文、全池解密、旧宽权限或删除账务事实。
- 真实实验费用、负债敞口、延迟/错误指标超过批准边界。

每次交接使用以下最小模板，不跨编号自行推进：

```text
工作包：Cxx / 本次子项：Cxx.n ...
状态：TODO / DOING / BLOCKED / LOCAL_PASS / STAGING_PASS / CANARY_PASS / ACCEPTED / DEFERRED
已完成：实现范围与实际证据
尚未完成：明确剩余项，禁止用“基本完成”替代
验证：runtime、数据库、命令/结果、是否 mock、是否真实外部调用
风险/授权：缺少的决策、权限、费用上限或环境
回滚：新流量开关、兼容版本、在途/账务处理
下一步：唯一推荐编号；前置门禁是否已满足
```

## 9. 参考口径与边界

- 技术实现以当前源码、真实测试和部署证据为准；[旧 parity 审计](./openrouter-parity-audit.md)仅作线索，不覆盖更新后的源码事实。
- [OpenRouter BYOK](https://openrouter.ai/docs/guides/overview/auth/byok)当前免费额度口径按计划及目录价推理费用描述；本平台可制定自己的政策，不复制动态页面缺失的具体数值。
- [OpenRouter 供应商接入](https://openrouter.ai/docs/guides/community/for-providers)可用于建立模态、价格、容量和合规支持矩阵。大量 Key 不等于独立账号容量，也不等于完整供给市场。
- [OpenRouter Batch](https://openrouter.ai/docs/batch-quickstart)为 Beta；实施时固定验证日期和支持子集，公开取消/结果下载不能凭其他厂商 API 形状猜测。
- Cloudflare 技能用于本清单的平台约束路由与官方事实核验；缓存参考中的数字/样例不作为不可变上线事实。新建云资源、付费实验和严格合规声明均保留独立门禁。
- Broker/KMS/Top-K 是本平台针对规模与安全提出的设计，不声称已知 OpenRouter 内部采用相同架构。

最终完成标准：**首发范围内每条“授权 → 有界调度 → 上游执行 → 结果确定性 → 资金/收益 → 对账恢复”链路均有可复现证据；范围外能力明确关闭或延期。**
